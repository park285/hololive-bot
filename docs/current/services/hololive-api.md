# Service: hololive-api

## Runtime identity

| Field | Value |
|---|---|
| Module | `hololive-api` |
| Binary | `hololive-api` |
| Quadlet unit | `hololive-api.service` (container `hololive-api`) |
| Port | `30001` (bot) / `30006` (admin) |
| Health endpoint | `https://127.0.0.1:30001/health` through container `./bin/healthcheck` |
| Ready endpoint | `https://127.0.0.1:30001/internal/ready` through container `./bin/healthcheck --api-key-env API_SECRET_KEY` (bot plane PostgreSQL·Valkey) |

## Role

bot/admin plane과 YouTube Community consume plane을 한 프로세스에서 호스팅하는 통합 runtime입니다.

- Bot plane: Kakao/Iris webhook ingress와 사용자 명령 routing, reply orchestration.
- Admin plane: dashboard-facing admin HTTP control plane, worker alarm HTTP client.

## Owns

- Kakao/Iris webhook ingress, user-facing command routing and reply orchestration (bot plane)
- Dashboard-facing admin HTTP API and the worker alarm client (admin plane)
- Bot-side alarm client
- Process-owned single ACL `Service` (bot pool, bot-plane `KAKAO_*` seed) shared by bot ingress and admin ACL routes
- Observation claim/finalize, canonical persist, notification intent, live-end finalizer, and retention (YouTube plane)
- `members.photo` Holodex PhotoSync product path (admin plane). YouTube channel photos are the `channel_photo` reducer.
- Gemini Decisions API broadcast type decisions for ended broadcasts the rules leave unclassified (`youtube_broadcast_type_decisions`, bot plane)

## Provides

| Contract | Type | Path/Event/Queue | Consumers |
|---|---|---|---|
| Iris webhook boundary | external HTTP/H3 | webhook/reply/send | Iris / Redroid |
| Admin HTTP API | HTTP JSON(저장한 일정 포스터 그림만 그림 바이트) | `/api/holo/*` (Console 계약 `iris-console/contracts/hololive/openapi.json`에 있는 operation만) | `iris-console` |
| settings.update | HTTP JSON + `settings.json` | `POST /api/holo/settings` | `iris-console`, `alarm-worker` |

## Consumes

| Dependency | Purpose | Failure impact |
|---|---|---|
| PostgreSQL | command/domain/admin data, subscriptions, outbox | command/admin failures, stale reads |
| Valkey | cache, rate limit, outbox wakeup, member epoch Pub/Sub, coordination(job lock) | degraded command, admin, and cache behavior |
| Iris | KakaoTalk ingress/reply automation | webhook/reply delivery failure |
| Alarm API | alarm CRUD/query | alarm commands and admin operations fail |

API 설정은 `internal/config`가 소유합니다. process 공유 자원(Valkey client, 멤버 캐시, bot·admin PostgreSQL pool,
ACL `Service`, Holodex·공식 일정 Service)의 조립과 정리는 `internal/app`의 `buildAPIInfrastructure`가 소유합니다.
Admin 조립·수명은 `internal/planes/admin/runtime`, router와 Stream handler는
`internal/planes/admin/internal/httpapi`에 있습니다. plane 사이 의존(admin→bot Iris 방 목록,
admin·bot ACL)은 `internal/app`이 같은 프로세스 인스턴스를 주입하며 loopback HTTP를 쓰지 않습니다.
Observation consume·canonical/retention과 private reducer는 `internal/youtube/`가 소유합니다.
Bot·admin은 필수 `ALARM_INTERNAL_URL`의 worker provider를 사용하며 in-process alarm service를 생성하지 않습니다.

## Must not own

- Alarm checker/scheduler loops owned by `alarm-worker`
- Claim and consumption of the PostgreSQL proactive delivery outboxes (`alarm_dispatch_deliveries`, `youtube_notification_outbox`) owned by `alarm-worker`
- Proactive Iris/Kakao notification egress owned by `alarm-worker`

## 관리자 멤버 쓰기

- 멤버 생성은 `CreateMemberRequest`로 저장 가능한 선택 입력을 유지하면서 이름·채널 식별자의 앞뒤 공백을 정리합니다. 이름은 필수이며 slug의 100자 한도와 각 저장 열의 문자 수 한도를 검증합니다. Unicode 문자 수 기준이며 선택 필드를 필수로 바꾸지 않습니다.
- `MemberAdminService`가 생성·졸업·이름·채널·별명 추가/삭제의 정본 저장 → 활동 기록 → 캐시 동기화를 소유합니다. 도메인 HTTP 핸들러는 필요한 의존성만 보유하며, 멤버 핸들러는 ACL·Iris 없이 구성됩니다.
- 생성은 HTTP 201, 나머지 변경은 HTTP 200과 기존 `status`·`message`를 유지합니다. 응답의 `persisted`, `cacheSynced`, `memberId`, `replayed`가 저장·전파·동일 요청 복구를 구분합니다. 저장 후 캐시 오류는 저장 실패 500으로 바꾸지 않고 `persisted=true`, `cacheSynced=false`와 경고 문구를 반환합니다.
- 생성 재요청은 slug 유일성 충돌 뒤 **모든 저장 입력과 현재 정본이 같은 경우만** 기존 ID로 캐시 동기화를 수행합니다. 새 행과 생성 활동 기록을 중복 추가하지 않습니다. 한 필드라도 다르면 HTTP 409 `Member already exists with different values`이며 기존 행을 덮어쓰지 않습니다. 자동 재시도·새 원천 fallback·마이그레이션은 없습니다.
- 동시 변경이 다른 요청의 snapshot warmup을 무효화한 경우에도 `cacheSynced=false`를 보존합니다. 오류를 성공으로 숨기거나 반복 갱신하지 않습니다. 요청 유실 뒤에도 동일 생성 요청으로 현재 정본 일치를 확인할 수 있습니다.
- Iris Console의 실제 Go 응답 projection은 기존 201/200·`status`·`message`로 위 응답을 수락합니다. 추가 필드는 현재 projection에서 제거되므로 Console 화면이 캐시 동기화 상태를 표시한다는 보장은 없습니다.
- 활동 기록은 기존 logger sink를 사용합니다. 캐시 실패 때문에 이미 저장된 변경의 기록을 건너뛰지는 않지만, DB commit과 로그 저장 사이의 프로세스 종료까지 원자적으로 보장하는 감사 outbox는 아닙니다.

## Admin 사용자 인증

- admin plane은 사용자 계정·세션을 소유하지 않습니다. Iris Console이 자기 세션으로 사용자를 인증하고 admin plane에는 `/api/holo/*`를 API key로만 호출합니다.
- 독립 대시보드 잔재였던 `/api/auth/*`(register·login·logout·refresh·me)와 `/oauth/callback`, auth service(Valkey `auth:*` 세션·bcrypt·로그인 rate limit), `ADMIN_ALLOWED_IPS`·`AUTH_BCRYPT_COST` 설정, `auth_users` 테이블(migration 348)을 제거했습니다. 비밀번호 재설정 경로와 `auth_password_reset_tokens`(migration 281)는 그보다 먼저 제거했습니다.
- 제거한 경로는 다른 미등록 경로와 같이 NoRoute 응답을 받습니다. API key가 없으면 401, 틀리면 403, 맞으면 404입니다.
- 다시 사용자 인증을 두려면 Iris Console 경계와 겹치지 않는 근거와 공개 API 계약 변경 승인이 먼저 필요합니다.

## Live query behavior

- `!라이브`는 기존 bot DB pool의 단일 snapshot으로 확정 방송과 채널 확인 최신값을 읽으며 원천을 호출하지 않습니다. 무인자는 우이를 포함한 활성 등록 Hololive 채널, 멤버 지정은 해석된 채널을 직접 조회합니다. freshness는 `min(5분, 2×poll interval+30초)`, 기본 270초이며 DB 조회 예산은 1초입니다.
- 공개·멤버 한정·최초공개의 fresh positive는 `/live`가 예정 영상이나 채널 페이지를 고르더라도 표시합니다. 방송 탭·Holodex 누락·absence slot은 채널 coverage가 아닙니다. 모든 채널의 신선한 음성 확인과 해소된 현재 후보가 갖춰진 빈 결과만 '현재 방송 중인 멤버가 없습니다.'로 안내합니다. 그 밖의 빈 결과는 '현재 방송 상태를 확인할 수 없습니다.'입니다. 멤버 지정 빈 결과의 `CMD_MEMBER_NOT_LIVE`와 100개 표시 한도는 유지합니다.
- 세션·head 없는 EXPLICIT_END와 session=ENDED는 완전성을 막지 않고 `live query incomplete`의 `nonblocking_diagnostics`로 남깁니다. LIVE/head 없음은 계속 차단합니다. 신선한 공개 불가 사실과 익명 수집에서 비공개·삭제 영상이 남기는 신선한 `identity_missing` UNKNOWN은 정상 head가 있는 stale LIVE 후보만 제외하며, 만료나 그 밖의 UNKNOWN 사유는 다시 차단합니다. pending을 삭제하거나 표시 전용 종료 상태를 만들지 않습니다. 사용자 응답에는 조회 사유·기준 시각·범위 설명을 붙이지 않습니다.
- YouTube plane은 `channel_live_check`를 최신값에만 저장하고 reducer로 보내지 않습니다. `video_live_check`의 identity가 맞고 유효한 upstream 종료 시각이 있을 때만 기존 명시적 종료 경로로 반영합니다. 공개 불가·해석 불가 UNKNOWN만으로 수명 상태를 바꾸지 않되, 시작을 관측한 LIVE 세션의 `identity_missing`이 `YOUTUBE_PLANE_LIVE_UNRESOLVABLE_GRACE_SECONDS`(기본 600초) 이상 이어지고 같은 채널의 신선한 `/live` identity 확인 음성이 있으며 신선한 positive가 없으면 `UNRESOLVABLE_VIDEO`로 끝냅니다(ended_at은 첫 `identity_missing` 시각, 알림 없음). UPCOMING 세션과 다른 UNKNOWN 사유는 종료 대상이 아닙니다. 다만 UPCOMING의 `identity_missing`·`identity_mismatch`는 추적만 하여 projection이 그 영상 확인 target의 재확인 주기를 추적 기간에 따라 2분→10분→30분→1시간으로 늦춥니다(10분·1시간·24시간 경계). 추적 시작 이후의 positive가 오면 다음 projection에서 2분으로 돌아오고, collector는 이전 긴 주기의 남은 대기 없이 현재 주기의 다음 slot에서 재확인합니다. head가 없는 `metadata_only`·`legacy_unknown` UPCOMING은 추적하지 않습니다. `!예정`·`!일정`과 Stream HTTP API는 기존 Holodex 원천·조직·기간·5분 캐시를 유지합니다. 응답 필드는 아래 Chzzk·Twitch 필드 제거 외에는 그대로이고, `org=all` 부분 실패의 응답은 아래처럼 바뀌었습니다.
- hololive-api process는 Holodex·공식 일정 Service를 하나만 만듭니다(`app.buildAPIInfrastructure`, bot plane의 `HOLODEX_*`·공식 일정 설정). bot(`!예정`·`!일정`)과 admin(`/streams/*`, PhotoSync)이 같은 인스턴스를 빌리므로 retry scheduler·cache-fill 조정이 process 하나로 묶이고, 종료는 모든 plane이 멈춘 뒤 process 조립이 한 번 합니다. 같은 `HOLODEX_API_KEY`를 쓰는 hololive-api와 alarm-worker는 분산 rate limit(`HOLODEX_DISTRIBUTED_RATELIMIT_ENABLED`, 기본 true)이 켜져 있으면 429 대기와 circuit open을 Valkey로 함께 지킵니다. 429의 `Retry-After` 시각은 `<bucket base>:cooldown`(기본 `holodex:api:cooldown`)에 뒤로만 밀리게 기록하고, 요청 승인 전후에 읽어 로컬 cooldown에 합칩니다. 로컬 breaker가 연속 실패로 열리는 순간에만 `<bucket base>:circuit_open`을 `SET NX PX 30000`으로 열며, 이미 열려 있으면 만료를 늘리지 않습니다. 요청 진입과 각 재시도 전에 이 key를 읽어, 열려 있으면 HTTP 요청 없이 503으로 거절합니다. 연속 실패 카운터는 process마다 따로 셉니다. 공유 상태의 Valkey 오류는 로컬 상태로 진행하고(fail-open) `hololive_holodex_shared_state_failures_total{operation}`과 Warn 로그로 드러냅니다. 호출자 취소·기한 만료로 끝난 읽기는 Valkey 오류로 세지 않습니다. 같은 Valkey를 쓰는 분산 rate limit은 계속 fail-closed입니다. 공유 key는 재시작 뒤에도 남으므로 비정상적으로 긴 `Retry-After`가 기록되면 그 시각까지 두 process가 기다립니다. admin plane 설정은 `HOLODEX_*`·공식 일정 env를 더 읽지 않습니다.
- Holodex live/upcoming 목록은 Service 인스턴스 안에서 같은 cache key의 미스를 조정합니다. owner가 조회·저장을 마치면 대기 caller가 캐시를 다시 읽습니다. caller의 취소/기한을 유지하고 결과 포인터나 오류를 공유하지 않습니다. cache write 실패·원천 실패·다른 process(collector·alarm-worker)의 요청까지 한 번으로 합친다는 보장은 없습니다.
- 원천 장애 때의 꼬리 지연(stack audit D10, T12 측정 기록, 동작 변경 없음): 실패는 캐시하지 않으므로 같은 key의 동시 miss는 한 명씩 원천을 다시 조회하고, k번째 caller는 앞선 k-1번의 실패 조회를 기다립니다. 2026-09-27 로컬 측정(Hololive `GetLiveStreamsByOrg`, 같은 key caller 6명, MockRequester가 100ms 뒤 응답, miniredis, 3회 반복)에서 성공이면 원천 호출 1번에 6명 모두 100–120ms에 끝났고, 실패면 원천 호출 6번에 완료가 100·200·300·400·500·610ms로 늘어났습니다. caller 기한을 350ms로 두면 3명은 원천 오류로, 3명은 350ms에 `context.DeadlineExceeded`로 끝났습니다(원천 호출 4번, 4번째 조회는 기한으로 취소). 운영 값은 측정하지 않았습니다. 코드상으로는 한 번의 실패 조회가 Holodex client의 시도당 제한(기본 20초)과 재시도·backoff로 길어질 수 있고, 연속 3번 실패하면 circuit breaker가 열려(30초) 이후 대기 caller는 원천을 부르지 않고 바로 실패합니다. 대기 시간의 상한은 각 caller의 ctx 기한입니다.
- `!라이브`는 YouTube만 조회합니다. Chzzk·Twitch client/설정/DI와 명령 내 플랫폼 병합은 제거했습니다. YouTube 조회 실패는 기존 조회 실패 응답으로 전달합니다. 멤버 저장 데이터와 프로필의 정적 링크는 보존하며 제공자 지원을 뜻하지는 않습니다. Stream JSON의 Chzzk·Twitch 필드 10개(`chzzk_channel_id`, `chzzk_live_id`, `chzzk_live_url`, `is_integrated`, `is_chzzk_only`, `twitch_user_id`, `twitch_user_login`, `twitch_stream_id`, `twitch_live_url`, `is_twitch_only`)는 채우는 생산자가 없어 제거했습니다. Stream HTTP 응답과 alarm dispatch event payload에서 이 키가 빠집니다. 알림 템플릿 함수 `trustedlink`도 YouTube 링크와 치지직 링크를 ` | `로 묶은 동시 송출 값을 두 줄 링크로 나누던 분기를 지웠습니다. 그런 값을 만드는 생산자가 없으며, 들어오면 다른 신뢰하지 않는 값처럼 `mdsafe`로 보호해 일반 문자로 표시합니다. Twitch·치지직 단일 링크는 Holodex `/users/live` 응답의 `link`가 `Stream.GetYouTubeURL`을 거쳐 알림 URL이 될 수 있어 신뢰 출처로 남깁니다.
- 새로운 자동 재시도·DB 실패 시 원천 전환·부분 결과 fallback은 추가하지 않습니다. 예약 retry 의미는 cache-fill 개선에서 변경하지 않았습니다.
- `org=all`에서 일부 org만 실패하면 provider는 성공한 org의 stream과 `PartialStreamsError`를 함께 돌려주고 캐시하지 않습니다(stack audit B1, T09). Stream HTTP API(`/api/holo/streams/live`, `/api/holo/streams/upcoming`)는 이 오류를 다른 원천 실패와 같이 500으로 응답하며 부분 목록을 내보내지 않습니다. 이전에는 부분 목록을 200으로 응답하고 캐시했습니다. 부분 목록과 실패 org를 함께 돌려주는 응답 필드는 공개 계약 변경이라 별도 결정 전에는 추가하지 않습니다. 소비자(iris-console admin-web의 streams 화면)는 한 org 장애 동안 `org=all` 조회 실패를 받습니다.

## Source fallback retirement

- 영속 reply INSERT의 접수 결과 불명(`ErrReplyStagingFailed`)과 Iris 전송 결과 불명은 같은 추가 응답 억제 규칙을 따릅니다. 도움말·달력 이미지 실패의 대체 텍스트나 공통 오류 응답을 추가하지 않고 명령 결과 불명을 보존합니다.
- Reply 발송은 Iris `202` admission과 `requestId` 저장에서 끝나고 행은 lease 없는 `accepted`가 됩니다. handoff 확인은 bot plane의 reply handoff reconciler가 맡으며 `failed`는 같은 행의 `:r1`/`:r2` 재발급(세대 상한 2, 예산 소진 시 `dead`), `outcome_unknown`·`404`·지평 미확인은 자동 재발송 없는 `manual_review`로 정산합니다. `last_error` 어휘는 `handoff_failed`, `handoff_outcome_unknown`, `handoff_status_missing`, `handoff_unconfirmed`이며, alarm-worker 발송 원장과 같은 값인 shared `pkg/contracts/alarm`의 `HandoffCode*`를 씁니다. 확인 간격과 재발송 예산 판정은 bot plane이 따로 소유합니다. 발송 정산은 caller 취소와 분리된 기존 `settlement_timeout_ms` 예산을 사용하며, 적용되지 않은 정산은 결과 불명으로 집계합니다. Reply outbox attempt `success`는 admission 완료를 뜻하고 handoff 완료 지표는 없으며 reconciler 결과는 로그와 manual review backlog로 관측합니다. 엄격 shape CHECK(migration 332)는 lease 있는 `accepted`를 거부하고, 만료 lease reclaim은 `submitting`만 다룹니다. `bot_reply_outbox_accepted_reclaimed_total`은 삭제했습니다. 확인 간격·전이표·관측·적용 전제·rollback 조건은 [API runbook](../runbooks/hololive-api.md#2-durable-webhook-or-reply-backlog-grows)을 따릅니다.
- 멤버 조회 backend 오류는 미발견 응답으로 바꾸지 않습니다. 달력 cache miss의 공유 조회는 기존 bot 명령 시간 예산으로 제한하고, 각 대기 요청은 자신의 context 취소에 따라 반환합니다. 달력 항목 스냅샷(`bot:calendar:entries:v1:<YYYY-MM>`, TTL `BOT_CALENDAR_ENTRY_CACHE_TTL_SECONDS`)과 렌더한 PNG(`bot:calendar:image:v5:<YYYY-MM>`, 값 앞에 항목 해시, TTL 7일)는 Valkey에 두어 인스턴스와 재시작 사이에서 공유합니다. 같은 달 항목이 바뀌면 PNG 월 key를 덮어쓰고, 차단 사진 대체 이미지처럼 공유하면 안 되는 렌더 결과는 저장하지 않습니다. 이 cache는 정본이 아니므로 Valkey 오류와 손상 값은 miss로 보고 PostgreSQL 조회·렌더로 진행하며 `render_failed`로 세지 않고 `calendar_entry_cache_failed`·`calendar_image_cache_failed` Warn 로그로만 드러냅니다. 호출자 취소·기한 만료로 끝난 cache 연산은 Valkey 장애가 아니므로 이 경고를 남기지 않습니다. 공유 멤버 캐시의 epoch 구독·재조회 작업은 공유 Valkey client와 bot·admin pool을 닫기 전에 종료합니다.
- bot·worker의 공유 방 Catalog는 같은 인스턴스에서 겹친 전체 HTTP 조회와 per-room 저장 순회를 공유합니다. owner의 전체 예산은 기존 `QueryTimeout.Default` 5초이며 initiator/follower는 각자 취소할 수 있습니다. owner가 저장 중 만료돼도 살아 있는 waiter는 이미 확보한 방 정보를 사용합니다. 완료 뒤의 miss는 새 조회가 가능하고 negative cache는 없습니다. DB 조회 오류의 HTTP fallback 금지, 명시적 webhook metadata 우선, unknown의 plain 처리와 동일 metadata의 `Observe` 저장 재시도는 유지합니다.

계약 없는 원천·표시 폴백을 오류 반환 단일 경로로 바꿨습니다. T18(2026-09-26) 30일 로그에서 아래 경로의 fallback·fail-open 경고는 0건이었습니다.

- Holodex `GetChannelSchedule`은 YouTube·공식 일정으로 보충하거나 그 결과를 캐시하지 않습니다([공식 일정 계약](../contracts/schedule-hololive-tv-api.md)). YouTube scraper로 부분 Channel을 만들던 `GetChannel`은 그 뒤 호출자가 없어 삭제했습니다.
- 멤버 matcher의 부분 일치 결과는 roster(`MemberDataProvider.LoadAllMembers`로 적재한 멤버 데이터) 이름을 채널명 정본으로 씁니다. Holodex 조회 보강과 그 실패 시 후보명·알림 멤버명 캐시로 채우던 체인은 없습니다. 정확 일치 결과와 같은 이름을 씁니다.
- `/api/holo` rate limit은 fail-closed입니다. rate limit이 켜져 있는데 cache가 없거나 limiter 초기화에 실패하면 admin API가 기동하지 않고, 판정 실패는 503으로 거절하며 `hololive_admin_rate_limit_check_failures_total`로 셉니다. `hololive_admin_rate_limit_fail_open_total`은 삭제했습니다.
- `domain.MemberDataProvider`는 오류를 돌려주는 `LoadAllMembers` 하나로 전체 멤버를 적재합니다. 공식 일정 식별 색인·멤버 목록 응답·alarm 콜라보 표시명은 멤버 적재 실패를 빈 결과로 바꾸지 않고 오류로 드러냅니다.
- 알림 멤버 표시명 폴백만 예외 계약으로 남습니다([alarm 계약](../contracts/alarm.md)의 멤버 표시명 예외 계약).

## 도움말·달력 이미지의 텍스트 대체 예외 계약

`!도움말`과 `!달력`은 이미지 응답이 정상 경로이고, 이미지가 확정적으로 실패했을 때만 같은 내용을 텍스트로 보냅니다(2026-10-02 계약화).

| 항목 | 계약 |
|---|---|
| Trigger | 이미지 적재·렌더링 실패나 빈 결과(`render_failed`), 또는 이미지 응답을 reply outbox에 기록하기 전에 난 실패(`send_failed`: transport·outbox writer·reply identity가 없거나 저장 payload 인코딩이 실패한 조립·인코딩 결함)입니다. `send_failed`는 Iris 전달 실패를 뜻하지 않습니다. Iris 전달은 기록 뒤 reply outbox 발송이 맡으며 그 결과는 명령에 돌아오지 않습니다. outbox 기록 실패(`ErrReplyStagingFailed`)는 행이 커밋됐을 수 있으므로 `send_failed`가 아니라 `outcome_unknown`입니다. |
| 한도 | 명령 한 번에 텍스트 응답 한 번입니다. 이미지 재시도는 없습니다. 이미지 전송 결과가 불명(`IsReplyOutcomeUnknown`)이면 이미 전달됐을 수 있으므로 텍스트를 보내지 않습니다(`outcome_unknown`). |
| 종단 | 텍스트 전송도 실패하면 두 오류를 합쳐 명령 오류로 반환합니다(도움말). 이미지 provider·renderer·전송 callback이 설정되지 않았으면 텍스트로 바꾸지 않고 명령 의존성 오류를 반환합니다. 운영 조립은 이 의존성을 항상 연결합니다. |
| Telemetry | `hololive_bot_image_text_fallback_total{command,reason}`(`command`: `help`, `calendar`; `reason`: `render_failed`, `send_failed`, `outcome_unknown`)와 Warn 로그(`help_image_fallback`, `calendar image ... falling back to text`) |
| Owner | `hololive-api` bot plane의 command handlers(`internal/planes/bot/internal/command/handlers`) |
| 검토 조건 | `render_failed`가 0이 아니면 이미지 렌더러 결함으로 보고 원인을 고칩니다. 두 명령의 `render_failed`와 `send_failed`가 90일 동안 0이면 텍스트 대체를 지우고 이미지 실패를 명령 오류로 반환합니다. |

## PhotoSync 재시도 예외 계약

admin plane PhotoSync는 `PHOTO_SYNC_ENABLED`(admin plane 기본 true)가 켜져 있으면 기동 10초 뒤 한 번, 그 뒤 7일마다 `members.photo`를 Holodex 채널 사진으로 갱신합니다. 한 주기가 실패하면 아래 범위에서만 같은 주기를 다시 시도합니다(2026-11-11 계약화).

| 항목 | 계약 |
|---|---|
| Trigger | 한 주기의 실패입니다. 갱신 대상(`channel_id`가 있고 `photo`나 `photo_updated_at`이 NULL이거나 7일보다 오래된 멤버) 조회 실패, 또는 대상이 있을 때의 Holodex 채널 목록 조회 실패가 해당합니다. 채널별 `members.photo` 저장 실패는 실패 수로만 세고 재시도하지 않습니다. 호출자 취소로 끝난 시도도 해당하지 않습니다. |
| 한도 | 주기마다 최대 3번 시도합니다. 재시도 전 대기는 5초와 10초이며 각각 0~2초 jitter를 더합니다. 각 시도의 Holodex 호출은 Holodex client의 자체 재시도와 circuit breaker를 그대로 거칩니다. |
| 종단 | 어느 단계든 3번 모두 실패하면 그 주기를 포기합니다. 다음 시도는 다음 7일 주기이거나 재기동 뒤 첫 동기화입니다. |
| Telemetry | 재시도 직전 Warn 로그 `Photo sync failed, will retry`(`attempt`, `max_attempts`), 최종 실패 Error 로그 `Photo sync failed after all retries`, 완료 Info 로그 `Photo sync completed`(`success`, `failed`, `total`)입니다. 전용 metric은 없습니다. |
| Owner | `hololive-api` admin plane의 PhotoSync(`internal/planes/admin/internal/photosync`) |
| 제거 조건 | 90일 동안 `Photo sync failed, will retry` 뒤 같은 주기가 `Photo sync completed`로 끝난 기록이 없으면 재시도를 지웁니다. 지우면 Holodex 일시 장애 때 다음 시도가 7일 주기 뒤로 밀리므로, 그 동작 변경을 CHANGELOG에 남깁니다. |

## 주간 일정 포스터

admin plane은 `SCHEDULE_POSTER_CONFIG_FILE`이 있으면 X·유튜브의 멤버 주간 일정 포스터를 수집하고, 확정한 포스터에서 일정표 행을 뽑습니다. 파일이 없으면 수집·일정표 행 추출·일정 변경 감지가 꺼지고, 관리 API(`/api/holo/schedule-posters*`)는 그대로 동작합니다. `!스케쥴`은 이미 저장된 행만 그리므로, 이 상태에서 관리 API로 확정한 포스터에는 "없음" 안내로 답합니다. `SCHEDULE_POSTER_GEMINI_API_KEY_FILE`(Gemini Developer API 키 파일)까지 있으면 후보를 자동 검토합니다. 잘못된 설정 파일, Vertex client 생성 실패, 잘못된 키 파일(절대 경로가 아님, 읽기 실패, 키 한 줄이 아님)은 기동 오류이며, 오류와 로그에는 키를 남기지 않습니다.

- 설정 파일(64KiB 이하, 모르는 키 거부): `{"poll_seconds":3600,"targets":[{"x_user_id":"<X 사용자 ID>","channel_id":"<YouTube 채널 ID>"}],"translation":{"project":"<GCP 프로젝트>","location":"global","glossary":{"ホロドリ":"홀로도리"}}}`. 대상은 `x_user_id`(X 계정), `"youtube_community":true`(그 채널의 유튜브 커뮤니티 글), `youtube_thumbnail_video_ids`(일정을 썸네일로 바꿔 다는 영상 ID, 11자, 대상당 5개 이하, 대상 전체에서 중복 불가) 가운데 하나 이상을 둡니다. 예: `{"channel_id":"<채널 ID>","youtube_community":true,"youtube_thumbnail_video_ids":["<영상 ID>"]}`. `poll_seconds`는 600~86400이고 기본 3600, `location`은 생략하면 `global`입니다. `project`와 `location`은 일정표 행 추출·번역과 변경 감지가 함께 쓰는 Vertex client의 설정입니다. `glossary`(선택, 200개 이하, 원문·번역 각 1~80자, 제어 문자 불가)는 멤버 이름 밖의 용어 표기입니다. `translation.rows.extract`·`translation.rows.translate`(선택)는 일정표 행 단계의 Vertex 호출 설정이며, 단계마다 `model`, `thinking_level`(`MINIMAL`·`LOW`·`MEDIUM`·`HIGH`), `temperature`(0~2, 생략하면 요청에 넣지 않아 모델 기본값), `timeout_seconds`(요청 하나의 상한, 30~900)를 둡니다. 생략한 키는 기본값(추출 `gemini-4-carbon` `LOW` 900초, 번역 `gemini-4-neon` `MEDIUM` 180초)을 쓰고, 한 단계의 일부 키만 넣어도 나머지는 기본값입니다. 설정 파일에 적은 키는 기본값보다 앞서므로, `translation.rows.extract`나 `translation.rows.translate`에 `model`·`thinking_level`·`timeout_seconds`를 직접 적어 둔 설정은 그 단계의 기본값이 바뀌어도 적어 둔 값을 계속 씁니다. 예: `"rows":{"translate":{"thinking_level":"HIGH"}}`. `rows`를 넣은 설정도 이 키를 모르는 이전 image가 읽지 못하므로 되돌리기 전에 뺍니다. 변경 감지의 `change_poll_seconds`, `translation.rows.match`, `translation.rows.decide`는 아래 "일정 변경 감지"에 있습니다. Vertex 인증은 `GOOGLE_APPLICATION_CREDENTIALS`(서비스 계정 ADC)로 공급합니다. Quadlet은 `HOLOLIVE_SCHEDULE_POSTER_ENABLED=1`일 때 `optional/schedule-poster` drop-in으로 두 파일을 mount합니다. 자동 검토 키는 `HOLOLIVE_SCHEDULE_POSTER_REVIEW_ENABLED=1`일 때 `optional/schedule-poster-review` drop-in이 `/etc/stack-secrets/hololive-bot/gemini/api-key`(키 한 줄, 실행 UID 전용 0600)를 mount합니다. 이 파일이 없으면 hololive-api 컨테이너가 시작하지 않으므로 키를 먼저 등록한 뒤 켭니다. 키 경로는 환경 변수라 이전 image는 무시합니다.
- 수집: `poll_seconds`마다 대상별로 FxTwitter(`api.fxtwitter.com`)의 게시물 목록을 최대 5페이지 읽습니다. 관리 API `POST /api/holo/schedule-posters/collect`(본문 `{}`)는 수집(자동 검토 포함)을 기다리지 않고 바로 한 번 예약하며 `{"queued":false}`면 이미 기다리는 요청과 합친 것입니다. 수집은 수집 goroutine 하나만 돌리므로 요청이 겹쳐도 동시에 돌지 않고, 다음 정기 수집은 앞 수집이 끝난 때부터 `poll_seconds` 뒤입니다. 설정 파일이 없어 서비스가 꺼진 배포는 이 경로만 503입니다. 응답은 시간순이 아니고 리포스트가 섞이므로 본인 원글만 보고, 지난 8일 안의 원글 가운데 사진과 일정 문구(`週間|今週|来週|スケジュール|schedule|weekly`, 대소문자 무시. 매일 올리는 「今日の配信予定」 공지는 받지 않음)가 함께 있는 글을 검토 대기 후보(`schedule_posters`)로 넣습니다. 첫 사진 URL이 `https://pbs.twimg.com`이 아니면 저장하지 않고 Warn 로그 `Schedule poster photo skipped: unexpected image URL`(`post_id`, `image_url`)을 남깁니다(Iris Console은 이 호스트의 원본만 표시합니다). 본인 원글이 모두 8일보다 오래된 페이지에서 멈춥니다. `youtube_community` 대상은 youtube-collector가 저장한 `youtube_community_posts`에서 지난 8일 안에 처음 관측된 글 가운데 같은 일정 문구(자동 검토가 켜져 있으면 문구와 본문 유무에 상관없이 모든 글)와 `yt3.ggpht.com` 이미지가 있는 글을 후보로 넣습니다.     2. 수집: FxTwitter로 그 계정의 게시물 목록을 읽어, 본인 원글 가운데 그 포스터의 글을 원장에 넣습니다(글과 멤버마다 한 번, 본문은 제어 문자를 공백으로 바꾸고 4000자까지). 다른 계정의 글을 인용한 원글은 본문 뒤에 `Quoted post by <작성자 이름> at <게시 시각> JST:` 줄과 인용한 글의 본문을 붙여 같은 4000자 안에 넣고, 판별·대응·근거 검증은 이렇게 붙인 본문을 봅니다. 본인 글 인용(방송 시작·감사 글에 딸린 지난 안내가 새 일정으로 읽히지 않게)과 지워진 글 인용은 붙이지 않습니다. 글이나 인용한 글에 유튜브 영상 주소(`youtube.com/live/<ID>`, `youtube.com/watch?v=<ID>`, `youtu.be/<ID>`, 글당 3개까지)가 있으면 공식 일정(`youtube_schedule_items`의 `hololive_official` 행)에서 그 영상을 찾습니다. 공식 일정이 콜라보 출연자를 적었고, 방송 시작이 글 게시보다 뒤이며, 글쓴이가 그 방송을 열거나(여는 채널은 같은 영상의 다른 출처 행에서 읽음) 출연자이면 본문 뒤에 공식 일정 블록을 붙입니다. 블록은 `Official schedule entry (this streamer is a guest):`(여는 쪽이면 `the host`) 줄 뒤에 `Start: <시작 시각> JST`, `Title: <방송 제목, 200자까지>`, 출연하는 쪽이고 여는 채널이 멤버일 때 `Channel: <여는 멤버 이름>`, `With: <함께하는 사람, 8명까지 적고 나머지는 and N others>` 줄을 둡니다. 블록까지 4000자를 넘으면 붙이지 않습니다. 같은 방송의 다른 출연자가 설정의 대상(`targets`)이면 그 멤버 앞으로도 같은 글 ID의 행을 넣습니다. 그 행의 본문은 글쓴이의 말 대신 `Post by <글쓴이 이름> about a stream this streamer joins.` 줄과 그 멤버 기준의 공식 일정 블록이고, 그 멤버의 게시 포스터 범위 안의 글일 때만 들어가며, 판별부터 따로 거칩니다. 방송을 여는 멤버 앞으로는 넣지 않습니다(그 멤버의 일정은 본인 안내 글이 반영). 다른 멤버 앞으로 갈 글은 프로세스 메모리에 8일 동안 두고 그 멤버를 처리하는 주기마다 넣으므로(같은 본문이면 바뀌지 않음), 글쓴이보다 먼저 처리된 멤버는 다음 주기에, 확정본이 아직 없는 멤버는 확정본이 게시된 뒤에 받습니다. 프로세스가 다시 뜨면 글쓴이의 글을 다시 읽을 때 채워집니다. 공식 일정이나 멤버 목록을 읽지 못하면 그 멤버의 글을 그 주기에 넣지 않고 저장소 오류로 올립니다(블록 없이 넣으면 나중에 본문이 달라져 다시 판정되기 때문). 이미 원장에 든 글은 다시 읽은 본문이 저장한 본문 뒤에 내용을 더 붙인 것일 때만(뒤늦게 붙은 인용 글이나 공식 일정 블록) 본문을 바꾸고 `unjudged`로 돌려 판별부터 다시 합니다. 그 글의 변경과 윤문은 지워지고, 뒤 글은 다시 대응하지 않으며, 철회한 글은 그대로 둡니다. 그래서 이 동작을 배포한 뒤 첫 수집(재시작 뒤라 수집 하한까지 깊이 읽음)에서, 그 주에 이미 수집한 글 가운데 인용 글이나 공식 일정 블록이 새로 붙는 글이 다시 판정됩니다. 쪽마다 마지막으로 나온 본인 원글(리포스트는 원글 시각을 달고 오므로 보지 않음)의 시각이 수집 하한 이전이거나 다음 쪽이 없으면 멈추고, 최대 10쪽을 읽습니다. 수집 하한은 포스터 게시 시각과 주 첫날 00:00 JST 가운데 늦은 쪽이고, 이 프로세스가 같은 (멤버, 포스터)에 대해 하한까지 닿은 수집을 저장까지 마쳤으면 그때 본 가장 늦은 글 시각으로 올라갑니다. 그래서 평소에는 1쪽에서 멈추고, 처음·재시작 뒤·게시 포스터가 바뀐 뒤에만 깊이 읽습니다. 10쪽을 읽고도 하한에 닿지 못하면 Warn 로그 `Schedule poster posts collection stopped at the page limit`을 남기고 하한을 올리지 않아 다음 주기에 다시 깊이 읽습니다. 한 쪽이라도 받지 못하면 그 주기에는 아무 글도 넣지 않고(Warn `Schedule poster change detection paused`, `stage`=`collect`) 이미 넣은 글로 계속합니다. 새 글을 넣으면 Info `Schedule poster posts collected`(`inserted`)를 남깁니다. 포스터의 글은 같은 채널에서 포스터 게시 뒤이고 주 첫날 00:00 JST부터 주 마지막 날 다음 날 00:00 JST 전까지 올린 글입니다. 이 범위는 저장소 쿼리 조각 하나(`queries/post_window.sql`)가 정하며, 수집·대기 목록·대응 기록·관리 API의 변경 목록·철회·되살리기가 모두 같은 범위를 씁니다.
    3. 대상 글: 멤버마다 주기당 20건까지 게시 순서로 고릅니다. 판별 전 글, 대응 전 글(되살린 글과 앞선 글의 기록으로 다시 대응하게 된 글 포함), 그리고 지금 게시 중인 행 묶음이 아닌 묶음에 대응했던 글(재추출이나 확정본 교체 뒤)이 대상입니다. 재추출을 기다리는 동안은 판별 전 글만 고릅니다.
    4. 판별: 자동 검토와 같은 키로 Gemini Decisions API(`gemini-decision-1`)에 본문 하나와 질문 둘(일정 정보가 있는가 `schedule_info`, 글의 종류 `announce`·`change`·`cancel`·`weekly`·`other`)을 한 요청으로 묻습니다. `schedule_info`가 기준값 이상이고 종류가 `weekly`·`other`가 아니면 `relevant`, 아니면 `not_relevant`입니다. 안전 차단 400은 글 사유 `blocked`로 닫고, Decisions의 세부 코드(`safety` 등)는 Warn `Schedule poster post failed`의 `error`에만 남깁니다. 글마다 한 번만 판별하고 재추출 뒤에도 다시 판별하지 않습니다. Info `Schedule poster post judged`(`status`, `schedule_info`, `kind`)를 남깁니다.
    5. 행 대응: 대응 모델(`rows.match`)에 검증한 지시문(`prompts/match.txt`), 글 본문과 게시 시각, 앞선 글의 변경까지 적용한 지금 일정 행을 주고, 검색 없이 JSON 스키마 구조화 출력으로 항목(20개 이하)마다 행 번호(없으면 null), 날짜, 시작 시각, 시간대, 상태, 글이 더한 내용(`text`), 근거 원문(`evidence`)을 받습니다. `text`에는 행이 이미 말한 방송을 다른 이름이나 더 넓은 이름(방송 종류, 해시태그, 애칭)으로 부르거나, 인사·홍보하거나, 행이 이미 정한 게임·기획 안에서 할 일을 말한 부분은 넣지 않게 지시합니다. 공식 일정 블록의 방송은 블록의 시작 시각으로 한 항목을 내고 제목·채널·함께하는 사람 줄을 `text`로 옮기되, 글쓴이의 말이 그 방송의 날짜·시각·상태를 다르게 말하면 글쓴이의 말을 따르게 지시합니다. 대응 직전에 게시 중인 행 묶음을 다시 읽어 앞 글의 기록을 담으며, 그 사이 묶음이 바뀌었으면 그 멤버를 이번 주기에서 멈춥니다.
    6. Go 검증·판정: 항목마다 형식·근거·대상 칸·날짜·시각을 검사하고, 통과한 항목을 대상 칸과 견줘 `same`, `time_changed`, `confirmed`, `tentative`, `cancelled`, `off`, `added`, `moved`, `moved_out`(주 밖으로 옮김, 원래 날짜에 취소로 남음), `content_changed`로 판정합니다. 24시 이상 표기(29:59까지)는 다음 날 시각으로 바꿔 견주고 저장 값은 글이 말한 표기 그대로 둡니다. 통과하지 못한 항목은 `rejected`와 사유 코드로 남습니다: `format`(날짜·시각·상태 형식이 틀리거나, `text`·근거가 500자, 시간대가 40자를 넘거나, 잘못된 UTF-8이나 NUL 문자가 있음), `foreign_zone`(시간대가 빈 값도 `JST`도 아님), `evidence`(근거가 비었거나, 공백과 줄바꿈을 모두 뺀 본문에 없음), `text_marker`(`text`에 코드가 붙이는 표지의 여는 쪽 `[update:`, `[badges:`, `[day off`, `[cancelled`가 있음, 대소문자 무시), `no_such_row`(없는 행 번호, 대상 칸 없는 취소, 방송 칸이 있는 날의 대상 없는 휴방), `date_range`(게시일과 주 첫날 가운데 늦은 날보다 이르거나, 주 밖으로 옮기는 것이 아닌데 주 마지막 날보다 늦음), `row_date`(취소·휴방의 날짜가 대상 칸의 표기 날짜와도, 24시 이상 표기를 바꾼 날짜와도 다름), `past_time`(추가·옮김·확정·시각 변경이 정한 시각이 게시 시각보다 이름. 이미 시작한 칸의 내용 변경인데 근거가 글쓴이 본인의 말이 아니라 인용한 글이나 공식 일정 블록에만 있는 항목도 같은 사유로 거절하며, 방송 뒤 감사 글에 딸린 지난 안내를 대응 모델이 가끔 항목으로 내기 때문. 지난 방송의 취소·휴방은 반영), `no_content`(대상 칸도 내용도 없는 새 방송), `slot_limit`(칸이 100개를 넘음), `duplicate_row`(한 글의 두 항목이 같은 칸을 가리킴), `time_collision`(글의 모든 항목을 반영한 뒤 같은 날 다른 방송 칸과 시작 시각이 같음. 걸린 항목을 빼고 다시 판정).
    7. 재번역: 카드에 변화를 만드는 변경 가운데 `text`가 있는 것만, 그 칸의 원문과 앞선 변경 메모를 행 번역과 같은 지시문(이름표, `glossary`, 같은 주에 먼저 정한 표기)으로 번역 모델에 보내 한국어 제목·함께하는 사람·장소·태그·메모를 채웁니다. 변경 메모(`[update: …]`)는 칸과 앞선 메모 가운데 어긋나는 부분만 바꾸며, 방송 시간대·장르·"방송" 같은 일반적인 말은 칸이 정한 방송 이름을 바꾸지도 거기에 더해지지도 않게 지시합니다. 행 번역과 같은 검사와 경고를 거치고 검증되지 않은 표기는 저장하지 않습니다. 재번역이 서비스 실패(아래 재시도 예외 계약의 대응과 같은 HTTP 상태 코드, Vertex에 닿기 전의 실패, 토큰 발급 실패)면 기록하지 않고 그 주기를 멈추며, 판정까지 끝난 결과를 프로세스 메모리에 들고 다음 주기에 대응 모델을 다시 부르지 않고 재번역부터 합니다. 그 밖의 실패(재시도를 다 쓴 검사 실패나 해석할 수 없는 응답, 503 밖의 5xx, 연결 뒤 시간 초과, 글 하나의 상한 초과, 포스터 주인이 멤버 목록에 없음)면 한국어 칸을 비운 채 변경을 저장하고 Warn `Schedule poster change translation failed`를 남깁니다.
    8. 저장: 글의 상태를 `matched`(도장은 포스터 id와 그 `rows_extracted_at`)로 바꾸고 그 글의 이전 변경을 새 변경으로 바꿉니다. 읽은 뒤 글의 상태나 도장이 바뀌었으면(다른 작업이 먼저 기록함, 철회, 앞선 글의 기록으로 다시 대응하게 됨) 기록하지 않습니다. 반영 변경(`same`·`rejected`가 아닌 변경)을 하나라도 기록하면, 같은 트랜잭션에서 같은 포스터·같은 행 묶음에 대응한 뒤 글(게시 시각, 글 ID 순서로 더 뒤이고 `matched`·`match_failed`인 글)을 `relevant`로 돌리고 사유와 도장을 비웁니다. 뒤 글의 판정 종류와 거절(`time_collision`, `past_time`, `duplicate_row` 등)이 앞선 글을 반영한 상태 기준이 되도록, 반영 변경을 기록한 뒤에는 그 멤버의 대기 목록을 다시 읽어 방금 기록한 글보다 뒤인 글을 같은 주기에 게시 순서대로 이어 처리합니다. 그래서 돌려보낸 글이 더 뒤의 글보다 먼저 다시 대응되며, 주기당 20건 한도에는 다시 읽은 뒤 처리한 글도 셉니다. 그 글의 변경 행은 지우지 않지만 도장이 비어 게시에서 빠지고, 다시 대응할 때 새 변경으로 바뀝니다. 철회한 글은 도장이 없어 돌리지 않고, 앞선 글은 고르지 않으므로 다시 대응이 되풀이되지 않습니다. Info `Schedule poster post matched`(`kinds`, 거절 `reasons`, `translated`, `translation_failed`, `warnings`, `doubts`)를 남깁니다. 처리할 수 없는 글은 `judge_failed`·`match_failed`와 사유(`unavailable`, `blocked`, `bad_answer`, `invalid_changes`의 닫힌 집합이며 관리 API 계약의 글 `reason` enum과 같음. 판별의 안전 차단도 `blocked`)로 닫고 Warn `Schedule poster post failed`(`status`, `reason`, 세부 원인 `error`)를 남깁니다. 실패 분류와 재시도는 아래 "일정 변경 감지 재시도 예외 계약"을 따릅니다.
  - 게시: `!스케쥴`과 변경 감지 입력은 지금 게시 중인 행 묶음에 대응한 `matched` 글의 변경 가운데 `rejected`를 뺀 것을 (글 게시 시각, 글 ID, 항목) 순서로 원래 행에 적용합니다. `same`도 글이 말한 날짜·시각·상태를 덮어, 늦게 기록된 앞선 글이 뒤 글이 확인한 값을 뒤집지 않게 하지만 변화로 세지 않습니다. 카드의 시각이 바뀐 칸은 이전 표시를 함께 그립니다. 카드의 날짜 칸이 그대로면 `23:00 → 25:00`처럼 이전 시각을, 다른 날 칸으로 옮겼으면 `금 → 02:00`처럼 원래 요일을 앞에 둡니다. 취소·휴방은 기존 취소·휴방 칸으로 그리고(같은 날 예정·미정 방송 칸이 있을 때, 그 방송이 글이 더하거나 옮겨 온 칸이거나 휴방이 글이 바꾼 칸이면 휴방 칸을 그리지 않습니다. 휴방으로 바꾼 뒤 그날 게릴라 방송을 더한 글 등. 포스터가 처음부터 같은 날에 휴방과 방송을 함께 적었으면, "휴방이지만 쇼츠 투고"처럼 둘 다 멤버가 한 말이므로 휴방 칸을 그날 맨 앞에 두고 둘 다 그립니다), 내용만 바뀐 칸은 강조하지 않되 번역된 제목·부연은 반영하며, 글이 더한 칸은 보통 칸으로 그립니다. 번역이 없는 새 칸은 제목을 "방송", 휴방 칸은 "휴방"으로 씁니다.
  - 관리 API와 Console: `GET /api/holo/schedule-posters/{id}/changes`는 그 포스터의 글(위 2번의 범위)을 돌려줍니다. 철회·되살리기를 할 수 있는 상태(`relevant`, `matched`, `match_failed`, `revoked`)의 글은 최근 200건까지, 나머지 상태의 글은 최근 50건까지 실어 응답은 최대 250건이고, 전체를 게시 시각 내림차순(같으면 글 ID 내림차순)으로 줍니다. 판별만 한 글이 많아도 조치할 글이 목록에서 밀려나지 않게 하기 위해서입니다. 글마다 `id`, `postUrl`, `postedAt`, `textExcerpt`(본문 앞 280자), `status`(위 상태와 `unjudged`, `revoked`), `reason`, `current`(지금 행 묶음에 대응한 글인가), `revocable`, `restorable`, `changes`(`current`인 글만, 항목 순서, `same`·`rejected` 포함: `item`, `kind`, `reason`, `slot`, `day`, `start`, `status`, `text`, `titleKo`)를 줍니다. 목록은 확정본이 아니어도 돌려주지만 그때 `revocable`·`restorable`은 false입니다. `POST /api/holo/schedule-posters/{id}/changes/revoke`(본문 `{"postId":"<글 ID>"}`, 응답 `{"id","postId"}`)는 `relevant`·`matched`·`match_failed` 글을 `revoked`로 바꾸고(도장과 사유를 비움) 그 변경을 지웁니다. 철회한 글은 되살리기 전까지 다시 판별·대응하지 않고 카드는 다음 요청에 다시 그려집니다. `POST /api/holo/schedule-posters/{id}/changes/restore`(본문·응답은 revoke와 같음)는 `revoked` 글을 `relevant`로 돌려, 다음 주기에 다시 판별하지 않고 그때 게시 중인 행 묶음에 다시 대응합니다. 두 경로 모두 포스터가 없으면 404, 포스터가 확정본이 아니면 409 `invalid_state`, 글이 없거나 그 포스터의 글이 아니면(다음 주 글 포함) 404, 글의 상태가 맞지 않으면 409 `invalid_state`이며 이 순서로 판정합니다. 일정표 행만 다시 뽑는 `POST /api/holo/schedule-posters/{id}/rows`와 칸 읽기 `GET /api/holo/schedule-posters/{id}/rows`는 위 "일정표 행"에 있습니다. 다섯 경로와 포스터 응답의 행 필드는 Console 포스터 상세의 일정표 상태와 칸, 행 다시 뽑기, 반영된 변경과 철회·되살리기를 위한 것입니다. 게이트웨이는 생성 계약에 있는 operation만 중계하고 계약에 없는 응답 필드는 지우므로, iris-console이 이 계약으로 생성 사본을 다시 만들어야 Console에서 쓸 수 있습니다. 계약은 [admin-api.openapi.json](../contracts/admin-api.openapi.json)이 소유합니다.
  - 지표: `hololive_schedule_poster_posts_total{outcome}`은 글의 판별(`not_relevant`, `relevant`, `judge_failed`)과 대응(`matched`, `match_failed`) 결과를 기록할 때마다 셉니다. `hololive_schedule_poster_change_cycles_total{result}`의 `paused`는 서비스 실패로 멈춘 주기, `store_error`는 서비스 실패로 멈추지 않았지만 어느 단계에서든 저장소 오류(수집한 글 저장, 게시 행·대기 목록·멤버·같은 주 표기 읽기, 판별·대응 기록, 다시 읽기, 보존 삭제)가 난 주기, `completed`는 서비스 실패와 저장소 오류 없이 끝난 주기이며 수집 실패나 불명 실패로 멤버 하나를 멈춘 주기도 `completed`입니다. 저장소 오류는 Error 로그 `Schedule poster task failed`(`task`=`changes`)로 드러납니다. `hololive_schedule_poster_change_last_completed_timestamp_seconds`는 마지막 `completed` 주기의 끝난 시각(Unix 초)입니다. 사유 코드는 라벨에 넣지 않고, 라벨 값은 기동 때 0으로 만들어 둡니다. 행 지표 `hololive_schedule_poster_rows_total`과 함께 admin plane이 기본 Prometheus registry에 등록하며, 같은 프로세스의 bot plane `/metrics` 리스너가 내보냅니다.
  - 보존: 글은 게시 60일 뒤 주기마다 100건씩 지우고 변경도 함께 지웁니다. 재추출·주 범위 수정·거절·확정본 교체는 원장을 지우지 않으며, 게시 중인 묶음이 바뀌면 그 묶음에 다시 대응합니다.
  - 한계:
    - 재추출로 새 행 묶음이 저장되면 옛 묶음에 대응한 변경은 곧바로 게시에서 빠지고, 다음 변경 감지 주기에서 다시 대응할 때까지(최대 `change_poll_seconds`와 대응 시간) 취소·지연이 빠진 원래 일정이 보입니다.
    - 뒤 글이 먼저 대응된 뒤 앞선 글이 늦게 들어와(수집 실패나 페이지 상한 뒤, 되살리기) 반영 변경을 기록하면, 뒤 글을 다시 대응할 때까지 그 글들의 변경이 게시에서 빠집니다. 보통은 같은 주기 안의 대응 시간이지만, 주기당 20건 한도를 다 쓰거나 실패로 그 멤버가 멈추면 다음 주기(최대 `change_poll_seconds`)까지 이어집니다. 다시 대응하다 불명 실패가 이어지면 종단 기준이 지날 때까지 빠진 채로 남습니다.
    - 철회는 뒤 글을 다시 대응하게 하지 않습니다. 철회한 글 뒤 글의 날짜·시각·상태 값은 게시 순서대로 맞게 덮이지만, 판정 종류와 거절(`time_collision`, `past_time`, `duplicate_row`)은 철회한 글을 반영한 상태 기준으로 남습니다.
    - 주 첫날 00:00 JST 전에 올린 글은 그날 게시 중인 포스터가 이전 주 포스터일 때만 그 포스터에 대응하므로, 주 시작 전에 올린 다음 주 변경 공지는 이전 주 포스터의 범위 밖 날짜라 거절(`date_range`)되거나 대응되지 않고, 다음 주 포스터에는 반영되지 않습니다. 이전 주 포스터에 행이 없어 다가오는 주 포스터를 게시하는 날에는 그 글이 어느 포스터에도 대응하지 않습니다. 거꾸로 주 마지막 날 다음 날 00:00 JST 이후의 글은 그 포스터의 글이 아니어서, 일요일 25시 같은 마지막 날 심야 칸에 관한 월요일 새벽 글은 이전 주 포스터에 대응하지 않고 그날 게시 중인 포스터의 글로 처리됩니다.
    - 변경 감지는 프로세스 하나의 goroutine 하나에서만 돈다는 전제입니다. admin 인스턴스를 둘 이상 띄우는 등으로 대응이 겹치면, 대기열 복귀와 상태 비교 뒤 기록이 앞선 글의 반영을 놓쳐 뒤 글이 앞선 글을 반영하지 않은 판정으로 `matched`에 남을 수 있고, 그 뒤 그 글을 다시 대응할 계기가 없습니다.
    - 서비스 실패가 아닌 재번역 실패(위 7번) 뒤의 변경은 날짜·시각·상태만 반영되고 한국어 칸이 비어, 내용 변경은 이전 제목이, 더한 칸은 "방송"이 보입니다. 그 글은 `matched`라 저절로 다시 번역하지 않으며, 행을 다시 뽑아 새 묶음이 저장되거나 앞선 글의 기록으로 다시 대응하게 되면 그때 번역합니다.
    - 판별 기준값은 200건 표본에서 정밀도·재현율 0.96이었습니다. 대응은 "같음"이 정답인 사례 23건 가운데 1건을 내용 변경으로 보았습니다(진짜 내용 변경 30건은 모두 맞음). 내용만 바뀐 칸을 강조하지 않는 이유입니다.
    - 다른 멤버의 글로 콜라보를 반영하려면 그 글이나 그 글이 인용한 글에 유튜브 영상 주소가 있고, 공식 일정이 그 영상의 콜라보 출연자를 적어 두어야 합니다. 공식 일정에 없는 방송, 출연자가 적히지 않은 방송, 공식 일정의 이름이 멤버 이름과 정확히 일치하지 않는 출연자는 반영하지 못합니다. 공식 일정은 여는 채널을 적지 않으므로 같은 영상의 다른 출처 행이 없으면 `Channel` 줄이 빠집니다.
    - 공식 일정은 글을 수집할 때 한 번 붙입니다. 그때 공식 일정에 아직 없던 방송은 프로세스가 다시 뜨거나 게시 포스터가 바뀌어 글을 다시 읽을 때에야 붙고, 붙인 뒤에 공식 일정의 제목·시각·출연자가 바뀌어도 그 글은 다시 판정하지 않습니다.
    - 이미 시작한 방송의 내용은 글쓴이 본인의 말로만 바뀝니다. 방송 중에 다른 사람의 안내 글을 인용해 알린 내용은 `past_time`으로 거절됩니다.
  - 배포와 롤백: 포스터 응답에서 필수 필드를 뺀 계약이므로 Iris Console 게이트웨이와 APK를 먼저 함께 배포한 뒤 hololive-api를 배포합니다. 옛 게이트웨이는 필드가 빠진 새 hololive-api의 포스터 목록·상세 응답을 502로 거절하고, 새 게이트웨이는 옛 응답의 남는 필드를 지우고 통과시킵니다. 그 사이 옛 hololive-api에는 칸 읽기 경로가 없어 Console의 일정표 칸 패널이 404로 다시 시도 상태가 되고, 옛 hololive-api는 확정 뒤 처리를 기다리는 포스터의 주 범위 수정을 계속 409 `invalid_state`로 거절합니다. 배포 전에 설정 파일에 이번 릴리스가 지운 Vertex 모델 키(CHANGELOG)가 없는지 확인합니다. 남아 있으면 모르는 키라 admin plane이 기동하지 않습니다. 키를 뺀 설정은 이전 image(v17.0.0)도 기본값으로 읽으므로 설정 파일 하나로 두 image를 오갈 수 있습니다. 이번 릴리스는 DB 열을 지우지 않으므로 hololive-api를 v17.0.0으로 되돌릴 수 있습니다. 되돌리면 v17.0.0이 확정 뒤 처리를 기다리던 행을 다시 처리해 그 Vertex 호출 비용이 다시 생기고, 이번 image에서 확정한 포스터는 v17.0.0도 다시 처리하지 않습니다. 이번 image의 거절은 남은 번역 상태와 번역 이미지를 지우지 않으므로, v17.0.0에서 번역을 마친 확정본을 이번 image에서 거절한 뒤 되돌리면 v17.0.0의 포스터 응답이 그 거절본을 번역 성공(`translationStatus=succeeded`, `translatedAt`)으로 보이고 `GET /{id}/translated`가 이미지를 돌려줍니다. 옛 Console은 확정본에만 번역본을 그리므로 화면에는 나오지 않고 `!스케쥴`도 행만 씁니다. migration 023은 되돌리지 않으며 v17.0.0도 같은 key를 읽으므로 바뀐 안내 문구가 나갑니다. 옛 게이트웨이와 APK는 v17.0.0 hololive-api와만 동작하므로, Console을 되돌릴 때는 hololive-api를 먼저 되돌립니다. 남은 열을 지우는 다음 릴리스의 migration을 적용한 뒤에는 v17.0.0으로 되돌릴 수 없습니다.

## 일정표 행 추출·번역 재시도 예외 계약

| 항목 | 계약 |
|---|---|
| Trigger | 행 추출 대기 포스터 하나의 단계 실패입니다. 추출(`rows_extract`)과 번역(`rows_translate`)의 Vertex 호출 실패, 후보 없는 응답, 512KiB를 넘거나 해석할 수 없거나 `rows` 배열이 없거나 100행을 넘는 응답, 위 "일정표 행"의 추출·번역 검증 실패가 해당합니다. Vertex가 요청 자체를 거절한 오류(HTTP 400·401·403·404)와 시간대 표에 없는 시간대의 행이 있는 추출 응답은 다시 보내도 같으므로 재시도하지 않습니다. 그림을 저장하지 않은 포스터의 원본 받기 실패, 포스터 주인 없음, 빈 `rows` 배열(일정 칸 없음)은 재시도 없이 종단입니다. |
| 한도 | 추출은 같은 요청을 3번 동시에 보내고 실행마다 최대 10번, 번역은 최대 10번 시도합니다. 번역을 다시 시도할 때 추출은 다시 하지 않습니다. 재시도 전 대기는 5초에서 시작해 두 배씩 늘고(각각 0~2초 jitter를 더함) 1분을 넘지 않습니다. genai SDK 자체 재시도는 1회로 고정합니다. 요청 하나의 상한은 단계별 `timeout_seconds`(추출 기본 900초, 번역 기본 180초)이고, 추출 단계의 상한은 2×추출 `timeout_seconds` + 150초(기본값으로 32분 30초), 번역 단계의 상한은 2×번역 `timeout_seconds` + 150초(기본값으로 8분 30초)이고, 포스터 하나의 상한은 둘의 합(기본값으로 41분)입니다. 각 단계에서 요청 하나가 시간 제한을 다 쓰고 한 번 더 보내도 끝나는 크기입니다. 추출 단계 상한이 지나면 아직 끝나지 않은 추출 실행을 끊고 그때까지 성공한 실행들로 정하므로, 늦은 실행 하나가 번역 몫을 쓰지 않습니다. 모든 호출이 실패하는 최악의 경우 포스터 하나가 추출 30번, 번역 10번을 씁니다. 세 실행이 모두 첫 응답부터 시간대 표에 없는 시간대를 돌려주면 추출 3번으로 `unsupported_zone`이 됩니다. |
| 종단 | 성공한 추출 실행이 2개 미만이거나(실행마다 10번 모두 실패, 재시도하지 않는 오류, 상한 초과), 번역이 10번 모두 실패하거나 재시도하지 않는 오류가 나거나, 포스터 상한을 넘기면 `rows_status=failed`와 `rows_error`(위 사유)를 기록하고 이전 행 묶음을 그대로 둡니다. 검증을 통과하지 못한 행은 저장하지 않습니다. 다시 시도하려면 관리자가 행만 다시 뽑기(`POST /api/holo/schedule-posters/{id}/rows`)를 예약합니다. 실패 사유는 포스터 응답의 `rowsStatus`·`rowsError`로 봅니다. 저장소 오류는 실패로 기록하지 않고 대기 상태로 두며 이 재시도 한도와 별개입니다. 모델 호출을 마친 뒤의 기록 실패는 결과를 프로세스 메모리에 들고 기록만 다시 하므로 모델을 다시 부르지 않습니다(재시작하면 한 번 더 추출). |
| Telemetry | 재시도 직전 Warn 로그 `Schedule poster translation attempt failed, will retry`(`poster_id`, `stage`=`rows_extract`|`rows_translate`, `attempt`), 종단 Warn 로그 `Schedule poster rows failed`(`poster_id`, `reason`), 성공 Info 로그 `Schedule poster rows recorded`, 지표 `hololive_schedule_poster_rows_total{result}`(`succeeded`, `failed`, `stale`, `store_error`)입니다. |
| Owner | `hololive-api` admin plane의 일정 포스터 서비스(`internal/planes/admin/internal/scheduleposter`) |
| 제거 조건 | 90일 동안 재시도 뒤 같은 포스터가 `Schedule poster rows recorded`로 끝난 기록이 없으면 재시도를 지웁니다. 지우면 일시 장애마다 관리자가 행 다시 뽑기를 눌러야 하므로 그 동작 변경을 CHANGELOG에 남깁니다. |

## 일정 변경 감지 재시도 예외 계약

| 항목 | 계약 |
|---|---|
| Trigger | 변경 감지 대상 글 하나의 판별(`change_decision`)·대응(`change_match`)·재번역(`change_translate`) 실패와 그 결과의 기록 실패입니다. 실패는 셋으로 나눕니다. 서비스 실패(어느 글도 처리할 수 없음): Decisions API의 이름 확인·연결 실패와 HTTP 400(안전 차단 제외)·401·403·404·429·503, 대응·재번역 Vertex 호출의 HTTP 400·401·403·404·429·503, Vertex에 닿기 전의 실패(이름 확인, 연결, TLS 인증서 검증 실패와 레코드 헤더 오류, 토큰 엔드포인트가 HTTP 오류를 돌려준 것을 포함한 토큰 발급 실패). TLS는 이 둘뿐이며 handshake 시간 초과와 상대가 보낸 TLS alert는 불명 실패입니다. 글 탓 실패(다시 보내도 같음): 판별의 안전 차단 400(Decisions 코드 `safety`, `prohibited_content`, `blocklist`, `image_safety`, `content_blocked`, 글 사유 `blocked`)·입력 차단(`blocked`)·해석할 수 없는 답(`bad_answer`), 대응의 입력 차단(`blocked`)·재시도 묶음의 모든 시도가 응답 해석 실패나 스키마 위반(항목 20개 초과, 512KiB 초과 포함)인 경우(`bad_answer`, 다른 실패가 섞이면 불명 실패)·검증한 변경이 저장 조건을 어김(`invalid_changes`). 불명 실패: 그 밖의 오류(연결 뒤 시간 초과, 503 밖의 5xx, 글 하나의 상한 초과 등)입니다. 서비스 실패가 아닌 재번역 실패는 글을 닫지 않는 재번역 실패로 따로 다룹니다(아래 종단). 호출자 취소로 끝난 시도는 기록하지 않습니다. |
| 한도 | 판별은 글마다 Decisions 요청 1번이며 다시 보내지 않습니다(요청 상한 2분). 대응과 재번역은 각각 최대 10번 시도하고, 재시도 전 대기는 일정표 행 추출 계약과 같습니다(5초에서 시작해 두 배씩, 각각 0~2초 jitter, 1분 이하). Vertex 요청 하나의 상한은 단계 설정의 `timeout_seconds`(기본 180초)이고, 글 하나의 대응과 재번역을 합친 상한은 10분입니다. Vertex HTTP 400·401·403·404, Vertex에 닿기 전의 실패, 입력 차단은 재시도하지 않고, 대응·재번역의 429·503은 재시도를 다 쓴 뒤 서비스 실패로 봅니다. 주기마다 멤버당 글 20건까지 처리하고, FxTwitter는 평소 1쪽, 처음·재시작 뒤·게시 포스터가 바뀐 뒤 최대 10쪽을 읽습니다. 모든 호출이 실패하는 최악의 경우 글 하나가 판별 1번, 대응 10번, 재번역 10번을 씁니다. |
| 종단 | 서비스 실패는 기록하지 않고 그 주기의 남은 멤버를 모두 멈추며, 다음 주기에 다시 합니다. 글 탓 실패는 바로 `judge_failed`·`match_failed`와 사유로 닫습니다. 불명 실패는 기록하지 않고 그 멤버를 그 주기에서 멈추며, 다음 주기에 다시 시도하다가 종단 기준이 지나면 `unavailable`로 닫습니다. 종단 기준은 판별이 `max(글을 원장에 넣은 시각, 이 프로세스가 그 글을 처음 판별하려 한 시각) + 6시간`, 대응이 `max(글을 원장에 넣은 시각, 행 묶음 저장 시각, 이 프로세스가 그 글을 그 행 묶음에 처음 대응하려 한 시각) + 6시간`입니다. 그래서 오래 대기열에 있다가 처음 판별하는 글과, 이전 확정본으로 돌아갔거나 재추출이 실패해 옛 묶음에 다시 대응하는 글도 첫 시도에서 6시간 동안은 닫지 않습니다. 첫 시도 시각은 프로세스 메모리에 판별은 (멤버, 글)별로, 대응은 끝난 결과와 함께 (멤버, 글, 포스터, 행 묶음 저장 시각)별로 두고, 기록에 성공하거나 그 글이 대기열에서 빠지면 지웁니다. 프로세스가 다시 뜨면 첫 시도 시각을 다시 셉니다. 대응·재번역을 마친 뒤 결과의 기록이 저장소 오류로 실패하면 다음 주기부터 모델을 다시 부르지 않고 기록만 다시 합니다. 재번역이 서비스 실패로 멈추면 판정까지 끝난 결과를 들고 다음 주기에 재번역부터 다시 합니다. 그 사이 앞선 글의 변경 내용(기록 시각 제외)이 달라지면 입력이 바뀐 것이라 대응부터 다시 계산합니다. 대응 결과의 기록이 종단 기준을 넘겨서도 실패하면 `match_failed`/`unavailable` 기록을 시도합니다. 프로세스가 다시 뜨면 들고 있던 결과가 없어져 한 번 더 계산합니다. 서비스 실패가 아닌 재번역 실패는 글을 닫지 않고 한국어 칸을 비운 변경을 저장합니다. 판별에서 닫힌 글은 다시 처리하지 않고, 대응에서 닫힌 글은 게시 중인 행 묶음이 바뀌거나 앞선 글이 반영 변경을 기록하면 다시 대응합니다. 관리자는 대응 전후의 글을 철회하고, 철회한 글을 되살릴 수 있습니다. |
| Telemetry | 재시도 직전 Warn 로그 `Schedule poster translation attempt failed, will retry`(`poster_id`, `stage`=`change_match`|`change_translate`, `attempt`), 멈춤 Warn 로그 `Schedule poster change detection paused`(`stage`=`collect`|`decision`|`match`, `channel_id`, `error`; `decision`·`match`는 서비스 실패와 불명 실패만), 글 종단 Warn 로그 `Schedule poster post failed`(`post_id`, `poster_id`, `status`, `reason`, `error`; 판별 안전 차단의 Decisions 코드는 `error`에 있음), 재번역 실패 Warn 로그 `Schedule poster change translation failed`, 모든 단계의 저장소 오류의 Error 로그 `Schedule poster task failed`(`task`=`changes`), 응답마다 Info 로그 `Schedule poster model usage`(`stage`=`change_decision`|`change_match`|`change_translate`), 지표 `hololive_schedule_poster_posts_total{outcome}`, `hololive_schedule_poster_change_cycles_total{result}`(`completed`, `paused`, `store_error`), `hololive_schedule_poster_change_last_completed_timestamp_seconds`입니다. |
| Owner | `hololive-api` admin plane의 일정 포스터 서비스(`internal/planes/admin/internal/scheduleposter`) |
| 제거 조건 | 90일 동안 불명 실패로 멈춘 글이 다음 주기에 `Schedule poster post matched`로 끝난 기록이 없으면 다음 주기 재시도와 대응·재번역 재시도를 지우고 첫 실패에서 닫습니다. 그 동작 변경을 CHANGELOG에 남깁니다. |

| 항목 | 계약 |

| Trigger | 자동 검토 중 다시 판정할 수 있는 실패입니다. 후보 하나의 실패(원본 내려받기 실패, 연결 뒤 응답 시간 초과, Decisions API·기간 읽기의 500 같은 서버 오류, 저장한 그림의 조회·저장과 확정·거절·넘기기의 DB 오류)와, 어느 후보도 판정할 수 없는 Gemini API 실패(이름 확인·연결 실패, HTTP 401·403·404·429·503, 400 가운데 잘못된 키 `API_KEY_INVALID`와 지원하지 않는 지역 `FAILED_PRECONDITION`)가 해당합니다. 그 밖의 400과 입력 차단·빠진 답·해석할 수 없는 응답은 후보 때문이라 재판정하지 않고 바로 관리자 검토로 넘깁니다. |

Gemini API 실패는 그 주기의 남은 후보를 멈춥니다. 주기마다 후보 20개, 후보마다 Decisions 요청 1번과 기간 읽기 요청 최대 1번입니다. 후보 하나는 들어온 뒤 6시간까지만 다시 판정하므로, 6시간 안에 판정할 수 있는 양은 주기당 20개에 그 안의 주기 수를 곱한 만큼입니다(기본 1시간이면 약 120개). `poll_seconds`를 6시간 이상으로 두면 실패한 후보는 다시 판정되지 않고 다음 주기에 넘어갑니다. 처음 켤 때는 지난 8일의 커뮤니티 이미지 글이 문구 거름 없이 한꺼번에 들어오므로, 이 양을 넘으면 판정하지 못한 글(일정표가 아닌 글 포함)이 관리자 목록에 쌓입니다. |

Console 알림은 주기마다 최신 후보 하나로 묶입니다. 자동 검토를 끄고 재배포하면 기다리던 후보는 다음 수집 주기에 모두 넘어갑니다. |

## 미분류 방송 유형 판정

bot plane은 `BROADCAST_TYPE_GEMINI_API_KEY_FILE`(Gemini Developer API 키 파일)이 있으면 제목·주제 규칙과 영상별 검토(`broadcast_type_rules.json`의 `reviewed_videos`)가 미분류로 남긴 종료 방송의 유형을 Gemini Decisions API에 물어 `youtube_broadcast_type_decisions`(migration 021)에 저장합니다. 경로가 비어 있으면 새 판정만 멈추고, 이미 저장된 판정은 방송 이력 분류에 계속 쓰입니다. 처음 켜기 전에는 표가 비어 있어 규칙과 검토로만 분류합니다. 잘못된 키 파일(절대 경로가 아님, 읽을 수 없음, 키 한 줄이 아님)은 bot plane 기동을 막습니다.

- 대상: 방송 이력 조회와 같은 주제·썸네일 보완(최신 LIVE 알림 이벤트)으로 규칙과 검토를 적용했을 때 미분류인 `ENDED` 세션 가운데, 현재 제목으로 물은 답이 없는 것입니다. YouTube player가 멤버 전용이라고 확인한 방송(종료 시각 확정 결과 `members_only` 또는 시청 가능성 `MEMBERS_ONLY`)은 묻지 않습니다. 멤버 한정은 형식보다 앞서는 유형인데 제목·썸네일로는 알 수 없어 잡담·게임 같은 형식으로 잘못 저장되기 때문이며, 이런 방송은 표시할 때 멤버십으로 분류합니다. 종료 시각 확정이 멤버 전용을 기록할 시간(종료 관측 3분 뒤 첫 확인, 결과를 모르면 30분 뒤 재확인)을 두려고 종료 관측 뒤 1시간이 지난 방송만 묻습니다. 기동 직후와 24시간마다 방송 이력 기간 전체(365일)를, 그 밖에는 10분마다 최근 3일을 최신순으로 훑습니다. 전체 훑기가 회차 상한에 걸려 끝나지 못하면 다음 회차가 다시 전체를 훑습니다.
- 질문: 방송마다 `POST v1beta/decisions`(`gemini-decision-1`) 요청 하나에 제목·주제를 담은 JSON 텍스트와 썸네일(`resolution` `medium`)을 공유 입력으로 넣고, `choice` 질문 하나로 10개 유형(`game`·`talk`·`singing`·`asmr`·`membership`·`event`·`horse_racing`·`watchalong`·`news`·`other`) 가운데 하나를 고르게 합니다. 공식 가이드 권고대로 선택지마다 설명을 달고 포괄 선택지 `other`를 두며, 제목·썸네일의 문구는 근거로만 다루라고 지시합니다. 여러 유형이 맞으면 `broadcast_type_rules.json`의 규칙 순서(멤버 한정 → 동시시청 → 노래 → ASMR·경마 → 이벤트 → 뉴스 → 일반 형식)대로 앞의 것을 고르게 해, 규칙이 분류한 방송과 기준을 맞춥니다. 질문과 선택지는 정렬해 직렬화하므로 같은 입력에는 매번 같은 요청을 보냅니다. 평가에서 같은 요청을 세 번씩 보낸 3건은 답과 확률이 모두 같았습니다. 썸네일을 내려받지 못한 방송은 제목만으로 묻지 않습니다.
- 저장: 고른 유형과 그 확률(`confidence`)을 `decided`로, 입력 안전 차단(HTTP 400의 `safety`·`image_safety` 등)은 답 없이 `blocked`로 저장하며 둘 다 다시 묻지 않습니다. 행은 물을 때의 제목과 함께 저장하고, 세션 제목이 바뀌면 그 행은 쓰지 않고 다시 묻습니다.
- 표시: `!방송이력`·`!방송시간`과 유형 필터는 규칙 → 영상별 검토 → player 멤버 전용 확인 → Gemini 판정 순으로 분류합니다. player 확인과 Gemini 판정은 규칙과 검토가 모두 미분류로 남긴 방송에만 씁니다. 규칙이나 검토가 정한 유형은 player가 멤버 전용이라고 확인해도 바꾸지 않습니다. player 확인은 방송이 끝난 뒤 다시보기의 접근 범위라, 공개로 방송한 뒤 다시보기만 멤버 전용으로 돌린 방송(예: 노래 방송)도 들어 있기 때문입니다. Gemini 판정은 `confidence`가 0.3 이상일 때만 씁니다. 0.3은 [표본 평가](../../review/broadcast-type-gemini-eval-20261115.md)로 정했습니다(holdout 정밀도 전체 0.933, 사람이 검토한 어려운 표본 0.810). 문턱은 읽을 때 적용하므로 바꿔도 다시 묻지 않습니다. 문턱 아래의 답과 차단된 방송은 미분류로 남습니다.
- 한도: 요청 사이 3초(요청 하나의 입력이 실측 약 1,150토큰이라 분당 약 2만 3천 토큰으로, 무료 등급 분당 5만 토큰을 일정 포스터 자동 검토와 나눠 쓰는 값), 회차당 판정 100건, 요청 하나 2분입니다. genai Go SDK에 Decisions client가 없어 REST로 호출하며 자체 재시도는 없습니다.
- 배포: Quadlet은 `HOLOLIVE_BROADCAST_TYPE_DECISION_ENABLED=1`일 때 `optional/broadcast-type-decision` drop-in(`43-broadcast-type-decision.conf`)으로 일정 포스터 자동 검토와 같은 키 파일 `/etc/stack-secrets/hololive-bot/gemini/api-key`를 다른 컨테이너 경로에 mount합니다. 파일이 없으면 hololive-api 컨테이너가 시작하지 않으므로 키를 등록하고 migration 021을 적용한 뒤 켭니다. 키 경로는 환경 변수라 이전 image는 무시합니다. 끄면 새 판정만 멈추므로, 저장된 판정까지 쓰지 않으려면 승인을 받아 `youtube_broadcast_type_decisions` 행을 지웁니다.

## 미분류 방송 유형 재판정 예외 계약

| 항목 | 계약 |
|---|---|
| Trigger | 방송 하나의 판정 실패입니다. 썸네일 내려받기 실패, Decisions API의 안전 차단이 아닌 400, 500 같은 서버 오류, 연결 뒤 응답 시간 초과, 해석할 수 없는 응답, 선택지 밖이거나 범위를 벗어난 답, 저장 DB 오류가 해당합니다. 어느 방송도 판정할 수 없는 Gemini API 실패(이름 확인·연결 실패, HTTP 401·403·404·429·503, 400 가운데 잘못된 키 `API_KEY_INVALID`와 지원하지 않는 지역 `FAILED_PRECONDITION`)는 그 방송을 실패로 기억하지 않고 회차를 멈추며, 다음 회차가 이어서 묻습니다. |
| 한도 | 호출 자체는 다시 보내지 않습니다. 실패한 방송은 그 회차에서 건너뛰고, 다음 전체 훑기 주기(24시간마다) 전까지는 최근 훑기에서도, 끝나지 않은 전체 훑기를 이어 가는 회차에서도 다시 묻지 않습니다. 연속 3건이 실패하면 그 회차를 멈춥니다. 썸네일의 모든 후보 URL이 HTTP 404인 방송(삭제·비공개 영상으로 봅니다)도 실패로 기억해 건너뛰지만, 연속 실패 수를 늘리지도 0으로 되돌리지도 않습니다. 실패 기억은 프로세스 메모리에만 있으므로 재기동 직후 전체 훑기에서 한 번 더 묻습니다. |

## Plane별 공유 자원

- `internal/app`의 `buildAPIInfrastructure`가 bot plane 설정으로 Valkey client 1개, `bot` PostgreSQL pool, 멤버 캐시 1개를 만들고(`BuildInfraModule`), admin plane용으로는 PostgreSQL pool(`admin`)만 따로 만듭니다. admin plane은 Valkey client와 멤버 캐시를 bot 것과 같은 인스턴스로 빌립니다. YouTube plane은 자기 `youtube_plane` pool을 만들고, 공유 Valkey client는 알림 행 commit 뒤 alarm-worker를 깨우는 신호에만 씁니다. 한 프로세스 안에 Valkey client 1개, 멤버 캐시 1개, PostgreSQL pool 3개(`bot`, `admin`, `youtube_plane`)가 있으며 `TestAPIInfrastructureSharesCacheButSeparatesRuntimePools`가 이 공유와 pool 분리를 검증합니다.
- plane에 넘긴 공유 자원에는 종료 권한이 없습니다. bot·admin·YouTube plane의 `CloseContext`가 각자 작업을 join하고(YouTube plane은 자기 pool도 닫음) 나면 process 조립이 공유 자원을 한 번 닫습니다. 순서는 공유 Holodex Service 정지 → 멤버 캐시(epoch 작업 정지와 대기) → `admin` pool → `bot` pool → Valkey client이며, 멤버 캐시의 epoch 작업이 Valkey client를 쓰기 때문입니다. bot·admin 가운데 자원 사용 작업이 join되지 않은 plane이 있으면 공유 자원을 닫지 않고 오류를 남깁니다.
- 장애 격리와 독립적인 드레인을 위해 PostgreSQL 풀을 실행 영역별로 나눕니다. Valkey 클라이언트와 멤버 캐시는 프로세스마다 하나만 둡니다. 2026-10-02에 plane별로 나눴던 Valkey client와 멤버 캐시는 v11.0.0(2026-10-19)에서 한 소유자로 다시 합쳤습니다.
- 멤버 캐시 비용은 시작 때 멤버 적재 1회, epoch 구독 연결 1개, 15초마다 epoch 조회 1회이며, 적재·재조회는 `bot` pool을 씁니다.

## Shorts observation processing

- 쇼츠 알림 초기화는 `SHORT` watermark와 저장된 canonical 영상이 소유합니다. 비어 있지 않은 유효 목록은 `PARTIAL / GAP_UNRESOLVED`여도 최초 기준 목록으로 저장하며 알리지 않습니다. 빈 부분 목록은 초기화하지 않고, 검증된 complete-empty 목록은 초기화합니다.
- 현재 writer는 빈 부분 목록만으로 초기화하지 않습니다. T18에서 구버전의 빈 부분 목록 초기화 잔여 행이 0건임을 확인한 뒤 해당 watermark를 미초기화로 되돌리던 분기와 보조 조회를 제거했습니다. 일반 영상으로 먼저 저장된 ID도 유효한 Shorts 기준 목록과 canonical 중복 판정에서 제외하지 않으며, 영상 종류를 강제로 변경하지 않습니다. 이미 저장된 목록이나 complete-empty 기준은 유지합니다.
- 초기화 이후 새 canonical video ID만 기존 `NEW_SHORT` outbox로 전달합니다. 이미 저장된 쇼츠는 알림 이력이 없어도 자동 backfill하지 않습니다. 기존 영상·watermark·전송 이력을 지우거나 가짜 `SENT`를 만들지 않습니다.
- `shorts_list`와 `video_list` claim은 같은 채널·kind의 더 앞선 `(scheduled_for, id)` 관측이 replay epoch 안에서 유효하고 `PENDING` 또는 `PROCESSING`이면 후속 관측을 선택하지 않습니다. 대기 중인 후속 관측의 attempt는 증가하지 않습니다. 다른 채널과 다른 kind는 이 순서 제약의 대상이 아니며, 기존 retry/lease recovery/dead-letter 정책은 유지합니다.
- 활성 backlog를 한 번 materialize하여 채널·kind별 선행 목록을 선택한 뒤 due 순서로 필요한 queue 행만 잠급니다. 완료 이력을 후보별로 재조회하지 않으며 custom/generic plan에서 전체 backlog 순회와 실제 claim 후보 조회를 따로 제한합니다.
- 관측 순서 제약을 적용하는 첫 배포에서는 기존 YouTube consumer를 drain한 뒤 교체해야 합니다. 이미 구버전에서 claim된 작업까지 새 claim SQL이 재정렬하지는 않습니다. source replay epoch 변경이나 과거 관측 일괄 replay는 배포 절차에 포함하지 않습니다.
- 부분 목록은 삭제·비공개 근거가 아니며 `earliest_complete_effective_at`을 채우지 않습니다. 최초 목록 이전의 관측이나 수집 범위 밖의 영상까지 복구한다는 보장은 하지 않습니다.

## 일반 영상·최초공개 신규성

- `video_list`는 항목별 공개 근거(Publication)를 싣는 generation 2(`VideoListPublicationContractGeneration`)만 받으며, 기준 시각 `earliest_baseline_effective_at`과 항목별 `novelty_pending`으로 신규성을 판정합니다. generation 1 관측은 지원 계약이 아니므로 consume 때 `unsupported_contract`로 DEAD_LETTER가 되며 canonical·replay에 반영하지 않습니다.
- 첫 유효한 비어 있지 않은 목록은 PARTIAL이어도 조용히 기준을 세웁니다. 빈 부분 목록은 기준이 아니며 complete-empty는 기준입니다. 기존 complete 기준은 보존하고 year-1 first-positive clock을 신뢰 가능한 과거 기준으로 추정하지 않습니다.
- 기준 이후 처음 발견한 영상은 신뢰 가능한 게시 시각이 기준 이후일 때만 알립니다. 과거에 게시됐지만 처음 목록에 나타난 영상은 알리지 않습니다. 게시 근거가 없으면 pending으로 저장하며 후속 증거가 확인되면 한 번 알립니다. 이미 알려진 canonical ID·다른 채널/Shorts에서 먼저 저장된 ID는 자동 backfill하지 않습니다.
- 새 미래 최초공개는 검증된 예정 시각으로 신규성만 닫고 발견 시 `NEW_VIDEO`를 만들지 않습니다. 같은 관측으로 확정한 live 세션(`is_premiere=true`)의 분 전·시작 알림이 공개 알림을 소유합니다(`contracts/alarm.md`). 기준 목록에 있던 최초공개와 공개 전환도 알리지 않습니다. 부분 목록은 끝까지 COMPLETE 부재 근거와 구분합니다.
- 요청 상한 안에서 증거를 확보하지 못하거나 목록 범위를 벗어난 영상의 알림 복구를 보장하지 않습니다. 이 정책은 알림 누락을 감수하고 과거 영상의 오알림을 막습니다.

## Collection projection heartbeat와 eligibility

- migration 261부터 `youtube_collection_projection_generations.valid_until`만 projection 만료의 정본입니다. target의 `valid_until`은 삭제합니다. API의 bot LiveQuery·수집 진단, collector acquire·Publish membership은 모두 유효한 CURRENT header를 요구하며, acquire의 bundle 조회 statement도 만료를 다시 검사합니다.
- API는 기존 projection guard를 입력 Build **이전**부터 한 번 배타 잠금합니다. READ COMMITTED에서 대기한 writer는 앞선 commit 이후의 입력을 읽으므로 오래된 Build의 역순 활성화를 막습니다. 조회·검증·저장 실패는 transaction을 rollback하며 validity를 연장하지 않습니다.
- header의 `validity_refreshed_at`은 마지막으로 수락한 supplied refresh 시각입니다. 그보다 최신이거나 PostgreSQL 마이크로초 정밀도에서 같은 시각이면 `valid_until`을 해당 시각+현재 TTL로 대체하여 설정 하향·상향을 모두 반영합니다. 더 과거 시각의 호출만 기존 만료를 보존합니다. migration 이전 시각은 NULL로 남기고 첫 성공 refresh에서 수립하며, 과거 TTL을 추정하지 않습니다. API 재시작 후에도 이 기준은 DB에 유지됩니다.
- `TestCollectionRealPolicyGuardCancellationAndExpiry`와 `TestCollectionRealPolicySharedGuardLoad`는 실제 PolicyBuilder/rosterReader의 10,000 target·영상 1,000개·현재 검토 500개·과거 영수증 15,000개에 독립 collector 공유 guard 조회 4개를 병행합니다. 실제 lock 대기, reader/writer 취소, 대기 중 header 만료 거부와 회복을 검증하고 30회 refresh의 guard/transaction p95·p99를 기록합니다. 이는 해당 DB 경로의 격리 부하이며 외부 provider부터 intent까지의 전체 지연이나 운영 지속 부하를 뜻하지 않습니다.
- `LiveCheckVideos` SQL은 구조적 LIVE/지난 일정·출처 미상 UPCOMING과 현재 원본에 적용되는 검토 영수증(`youtube_live_review_current_receipt`, migration 262) 제외를 cap+1 이전에 적용하고, 같은 statement의 DB 시각과 필요한 사실만 반환합니다. API가 미래/NULL 근거를 거부하고 밀리초 단위 기존 예산으로 positive/availability deadline을 계산합니다. notification/operational/live 입력은 READ COMMITTED의 별도 statement이며 하나의 공통 snapshot이라고 보장하지 않습니다. 지연된 refresh 호출 시각은 기존 header validity를 줄이지 않습니다.
- 구조 identity(subject/kind/priority/cadence/enabled)가 같으면 generation/hash와 연속 `member_since_generation`·`created_at`을 유지합니다. 실제 `not_before` 변경 row만 UPDATE하고 같은 transaction에서 header의 양수 `eligibility_version`을 한 번 올립니다(새 generation 기본값 1). 변경 없는 heartbeat는 header만 쓰며 target/reason 행을 갱신하지 않습니다. 이유만 바뀌면 기존처럼 이유를 교체하되 eligibility version은 바꾸지 않습니다.
- collector는 현재 header·target·lease를 같은 후보 statement에서 확인하는 관계형 조회를 유지합니다. 전체 target/lease를 캐시해 AP에서 정렬하는 안은 전송량 회귀로 채택하지 않았으며 target별 eligibility version도 추가하지 않습니다. 기존 상한 10,000 targets/50,000 reasons/1,000 live 입력, membership·lease/fence·DB slot·원자적 Publish와 기존 bounded retention의 CURRENT/STAGING·lease 보호, collector의 reasons/canonical 접근 금지는 유지합니다.
- IDLE 대상의 관측 due는 scheduler와 같은 `LEAST(next_due_at, scheduled_for + 현재 bundle cadence)`이며 `eligible_at`보다 앞당기지 않습니다. cadence 연장 때 이미 도래한 slot을 늦추지 않고 ACTIVE 만료·DEFERRED 재시도·projection 만료의 의미는 유지합니다.
- header validity 구조는 epoch-3 baseline(`001_schema_epoch3_baseline.sql`)에 포함되어 있으며 별도 선행 migration이 없습니다. 이 구조를 모르는 이전 API·collector binary와 혼합 운용하지 않고, 롤백 경계는 [migration 규약](../../../hololive/hololive-api/scripts/migrations/CONVENTIONS.md)의 epoch-3 적용과 복구 하한을 따릅니다.

## Live canonical 저장과 잠금 순서

- `youtube_live_sessions`·`youtube_live_reconciliation_heads`·`youtube_live_pending_ends`·`youtube_video_availability`의 writer는 `internal/youtube/sourceobservation` 하나입니다. worker·collector의 참조는 읽기 SQL입니다.
- 세션의 status·관측 시각·메타데이터 정책(ENDED 유지, LIVE→UPCOMING 후퇴 방지, 필드별 관측 시각 우선순위, 저장된 채널·`ended_at` 유지)은 `live.Reduce`·`live.FinalizeDue`와 `schedule.Reduce`가 정합니다. 저장은 잠금 안에서 읽은 행과 결과를 비교해 바뀐 행만 씁니다. 읽은 행이 있으면 그 행 전체가 그대로일 때만 적용되는 `UPDATE`(`repository_live_session_update.sql`), 없으면 `INSERT … ON CONFLICT DO NOTHING`(`repository_live_session_insert.sql`)이며 SQL은 값을 병합하지 않습니다. 0행 적용은 `LiveSessionConflictError`로 보고하고 트랜잭션을 되돌리며, YouTube plane은 이를 40001과 같은 재시도 대상으로 분류합니다. 최초공개 분류는 `is_premiere`가 NULL일 때만 채우는 별도 SQL을 유지합니다.
- `0048` head 저장은 18개 mutable 필드 전체의 `IS DISTINCT FROM`으로 같은 근거의 tuple rewrite를 피하며 `updated_at`·review snapshot을 유지합니다. 실제 사실 시계·ignored-absence 변화는 계속 저장합니다.
- `youtube_live_runtime_state`는 원본 트리거가 아니라 writer가 같은 READ COMMITTED 트랜잭션 끝에서 `refresh_youtube_live_runtime_state(text[])`를 한 번 호출해 갱신합니다(migration 328). 관측 writer는 `ReconcileResult.LiveRuntimeVideoIDs`(finalizer는 decision의 세션·pending key)를 넘기며 빈 key는 DB를 호출하지 않습니다. 함수는 READ COMMITTED가 아니면 `live runtime refresh requires read committed transaction`으로 거절하고, 영상 key를 1024개 bucket으로 접은 advisory 잠금을 bucket 순으로 잡은 뒤(같은 영상은 커밋까지 직렬화, 전체 재계산도 잠금 표를 고갈시키지 않음) 문장별 새 snapshot으로 원본을 다시 읽어 행을 지우거나 바뀐 행만 upsert합니다.
- 전역 잠금은 같은 advisory key의 두 모드입니다. 관측 writer는 `lock_youtube_live_runtime_state_shared()`, 증거 retention·수동 영수증(`record_youtube_live_review`)·terminal head 복구·라이브 원본을 바꾸는 data migration은 `lock_youtube_live_runtime_state()`(exclusive)를 원본 잠금보다 먼저 잡습니다. 관측 writer끼리는 원본 행 잠금과 영상 잠금으로만 직렬화되며, 그 사이의 40001·40P01·55P03과 `LiveSessionConflictError`는 YouTube plane의 관측 재시도로 처리합니다.
- 아래 표는 경로별로 잡는 잠금을 앞에서 뒤 순서로 적습니다. "갱신"은 트랜잭션의 마지막 공유 쓰기인 `refresh_youtube_live_runtime_state`이며 영상 잠금을 잡은 뒤에는 다른 행 잠금을 기다리지 않습니다.

## Observation storage and retention

- 채널 수치 통계·구독자 수 명령·통계 알림은 제거합니다. 채널 profile/photo, 방송·일정과 알림 구독은 유지합니다.
- 각 successful collection slot의 관측은 독립 저장합니다. payload만 kind/schema/canonical profile과 전체 32바이트 SHA-256으로 공유하며, JSONB의 PostgreSQL LZ4 압축을 사용합니다. identity와 외부 hex hash 계약은 바꾸지 않습니다.
- claim은 같은 SQL에서 payload를 조회합니다. 참조 누락·kind/schema 불일치·hash 손상은 오류이며 구 저장 경로로 되돌아가지 않습니다. GC는 참조가 없는 payload만 잠금 후 새 snapshot으로 확인하여 제한된 수만 삭제합니다.
- claim SQL은 due 행 중 replay epoch 이전 자동 claim과 시도 소진 행을 다른 선점 후보와 함께 잠그기만 합니다. DEAD_LETTER 여부와 사유(`replay_epoch_expired`가 `attempts_exhausted`보다 우선)는 Go 재시도 정책이 정하고, 같은 claim 트랜잭션의 집합 UPDATE 한 번으로 claim 트랜잭션 시각·NULL 상세와 함께 기록합니다. claim 시점 DEAD_LETTER는 지표를 남기지 않습니다.
- application은 entity별 멱등·CANONICALIZED 결과를 한 INSERT로 저장하며 원본의 `ON DELETE CASCADE` 수명을 따릅니다. 고아 유예·별도 감사 retention은 없습니다. provider/kind/subject/hash/effective clock은 원본에서 읽고 감사 행에 중복 저장하지 않습니다.
- 원본·live/content absence slot의 scope/evidence SHA-256은 32바이트 `bytea`로 저장합니다. publisher/claim/reducer 경계에서는 기존 소문자 hex 표현과 동일한 identity·dedup 비교를 유지합니다.
- 원본 retention은 큐·종료 근거, CURRENT/STAGING generation, ACTIVE 수집 lease, LIVE/UPCOMING 세션별 최신 application 근거와 pending-end 근거를 보호합니다.
- migration 315의 원본 정리는 보호 판정 전에 최대 1,000개 ID를 materialize합니다. kind별 인덱스 후보 반환은 최대 1,000개(정책 최대 16개), 최초 보호 검사는 합계 최대 1,000개이며 삭제·최종 보호 재검사는 `BatchSize`(최대 1,000) 이내입니다. 이 상한은 물리 I/O·보호 함수 내부의 자식 조회량·FK 쓰기량·실행 시간의 상한이 아닙니다.
- `(received_at,id)` 진행 커서와 고정된 순회 상한을 DB singleton에 보존합니다. 새 유입이 계속되어도 순회 끝에서 앞쪽을 재방문하고, 잠긴 후보는 건너뛴 뒤 다음 순회에서 다시 봅니다. 모든 kind가 같은 시간/ID 순서를 공유하며 보호 해제·늦게 삽입된 앞쪽 원본도 재방문합니다. 커서와 원본/application 삭제는 같은 transaction으로 확정·롤백하므로 재시작 때 처음부터 훑지 않습니다.
- DB 함수가 exclusive live 전역 잠금 → 커서 → 원본 잠금을 소유합니다. 전부 보호된 창도 성공한 tick이며 payload·absence·checkpoint 정리는 계속 실행됩니다. 앞 단계의 별도 commit 수량과 `BacklogKnown=false`의 미확정 의미는 유지합니다. runtime·scraper는 커서 표에 직접 접근하지 않습니다.
- publish·claim·application SQL이 요구하는 provenance·어휘 사전과 bytea 키는 epoch-3 baseline(`001_schema_epoch3_baseline.sql`)에 포함되어 있으며 별도 선행 migration이 없습니다. 이 구조를 모르는 구 binary나 이전 migration runner를 같은 DB에 섞어 실행하지 않습니다. 감사 표의 물리 공간 회수(`VACUUM FULL`)에는 별도 점검 창·백업·용량 확인이 필요하며 로컬 검증은 운영 DDL·배포 승인이 아닙니다.
- RETIRED projection 기본 보존은 2일이며 reasons+targets 합계를 batch 상한 이하로 제한하고 CURRENT/STAGING, lease 참조 generation을 보호합니다. 호출 timeout은 8초입니다.
- 운영 cutover와 복구 경계는 [API runbook](../runbooks/hololive-api.md#youtube-관측-저장-구조-전환)을 따릅니다. 소스 기본값 변경은 운영 TTL 적용 완료를 뜻하지 않습니다.

- PostgreSQL and Valkey availability
- `ALARM_INTERNAL_URL` and API key configuration for the alarm-worker client
- Internal HTTP/H3 client options (alarm-worker client) are loaded once into `BotPlaneConfig.InternalH3` and `AdminPlaneConfig.InternalH3` and passed explicitly; each plane owns timeout and transport cleanup. Iris URL-file dynamic reload remains on its existing path.
- The process lifecycle uses the same shared-go `bootstrap` and `lifecycle.Run` assembly as youtube-collector and alarm-worker. It is not an operator-selectable mode and does not change ports, routes, config keys, or dependency readiness requirements.

## Shutdown behavior

- 통합 `Runtime.Run`(shared-go `lifecycle.Run`)이 process signal의 유일한 소유자입니다. 조립은 process 공유 자원(`buildAPIInfrastructure`) → bot → admin → YouTube plane 순서이며, 뒤 plane은 앞에서 만든 in-process 인스턴스를 빌립니다. YouTube plane은 worker profile의 `source_observation` executor가 꺼져 있어도 항상 만들고 시작하며, 이때는 영속 큐 표본 수집만 돌립니다. 시작은 YouTube → admin → bot 순서이고, 종료는 runtime context를 취소한 뒤 bot → admin → YouTube 순서로 drain합니다.
- Stop HTTP/H3 ingress and scheduler workers within one shared 10-second plane-drain budget. Drain plus plane cleanup is a hard 30-second cap: as with the former Fx stop timeout, a plane that ignores cancellation is abandoned at the deadline and the bootstrap `Close` does not re-join unfinished cleanup. Only the telemetry flush (at most 5 seconds) and logger close follow, inside the unit's 45-second `StopTimeout`.
- Plane `CloseContext` receives the remaining process-stop context. Each plane joins its background tasks before releasing the resources it owns (the YouTube plane also closes its `youtube_plane` pool); bot durable samplers are included. The shared Valkey client, member cache and bot·admin pools are released once afterwards by the process assembly (see "Plane별 공유 자원"). A join timeout preserves live resources and the error; the process then exits without re-joining or starting concurrent cleanup, and cleanup that has not started by the stop deadline is not started.
- YouTube claim release waits for the claim producer to finish registering its returned batch. Registration and fenced release share the existing settlement budget; if registration times out, a later `CloseContext` can finish that release. An attempted release failure is retained without automatic retry, and DB cleanup still waits for all workers to join.
- Bot readiness cancellation is normal only when its error matches the runtime's actual shutdown cancellation. An independent readiness deadline or a joined operational error remains fatal.
- A runtime fatal, plane-drain failure, or process-stop timeout remains process-fatal. Cleanup is attempted once and no legacy lifecycle fallback is selected.
- Do not drain or mutate dispatch queues during shutdown.
- Preserve delivery/outbox state in PostgreSQL.

## Observability

- Logs: `sudo journalctl -u hololive-api.service -f`
- Health: `https://127.0.0.1:30001/health`, `https://127.0.0.1:30006/health` through container `./bin/healthcheck`
- Ready: `https://127.0.0.1:30001/internal/ready` through container `./bin/healthcheck --api-key-env API_SECRET_KEY`
- Metrics: bot plane이 `HOLOLIVE_METRICS_ADDR`에 평문 HTTP/1.1 `/metrics` 리스너를 엽니다(값이 비면 열지 않음). admin plane은 따로 metrics 리스너를 두지 않고, admin plane이 기본 Prometheus registry에 등록한 지표(`hololive_admin_rate_limit_check_failures_total`, `hololive_schedule_poster_*`)도 이 리스너가 함께 내보냅니다. 운영 주소·인증과 조회 명령은 [API runbook](../runbooks/hololive-api.md#go-runtime-metrics-prometheus)을 따릅니다.
