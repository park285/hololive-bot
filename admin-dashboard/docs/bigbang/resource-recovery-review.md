# RSS 회복 측정 시작점 변경 기록

2026-09-10, `PLN-20260909-hololive-admin-bigbang-replacement` T10/V06. 사용자가 초기화 후 측정 시작을 승인하여 **짧은 진단에 적용**했습니다. 기존 실패와 정규 검증의 동결 조건은 유지합니다. 이 문서의 절차 변경 자체는 PASS 증거가 아닙니다.

시작점 변경을 검토한 당시의 후보 `b9e9210a…`는 [동일 조건 부하 비교](native-performance-valkey-pools.json)에서 7개 API p95 예산과 구형 대비 RSS 예산을 충족했습니다. RSS는 구형 60.9 MB, 후보 36.3 MB입니다. 반면 [10분 회복 검사](resource-soak-valkey-pools.json)는 시작 1분 p95 33.4 MB보다 마지막 1분 median 35.9 MB가 커서 실패했습니다. FD·goroutine·연결 및 polling 정리는 통과했습니다.

[재연결 없는 동일 이미지의 6분 대조 관찰](resource-soak-no-churn-control.json)도 시작 RSS p95 33,058,816→마지막 median 33,820,672 bytes로 같은 회복 조건에 실패했습니다. 72개 표본·16 WS·heartbeat·한도 거부·종료 후 정리를 확인했고 오류·업무 효과는 0입니다. 이 결과는 관찰 완료이며 PASS가 아닙니다. 시작 직후 기준을 검토할 근거이지만, 재연결 시험의 RSS 증가 전체를 설명하거나 누수 부재를 보장하지는 않습니다.

현재 시작 구간에는 최초 상태 이력이 채워지는 과정이 포함됩니다. `observations/hub.go`의 이력은 2초 주기로 최대 30개를 보관하고, `stream_frames.go`는 재연결 때 이 이력을 다시 직렬화해 전달합니다. heartbeat는 현행 짧은 검사에서 5분에 처음 실행합니다. 따라서 시작 구간과 후반 구간에 실행된 초기화 경로가 같지 않습니다. 이것만으로 재연결 후 RSS 증가 전체를 설명하거나 누수 부재를 단정하지 않습니다.

승인하여 적용한 변경은 짧은 진단의 **측정 시작점**입니다.

1. 현재와 같이 4개 family·16개 WS를 연결하고 60초 동안 정상 프레임을 받아 최대 길이 이력을 채웁니다.
2. 각 family의 heartbeat와 각 WS의 재연결을 한 번 실행해 측정에 사용할 실제 경로를 미리 실행합니다. 이 구간도 별도 표본으로 보존하고, 측정할 100회 재연결에 합산하지 않습니다.
3. 이어지는 10분 동안 기존 16 WS·100회 재연결·5초 표본을 유지합니다. **마지막 1분 median ≤ 시작 1분 p95**라는 수치 기준과 종료 후 연결·polling 정리는 그대로 검사합니다. 총 소요 시간에는 앞선 초기화 구간이 추가됩니다.
4. CPU 2개·128 MiB·GOMAXPROCS·GOGC·GOMEMLIMIT, p95 +15%와 구형 대비 RSS +10% 예산은 유지합니다. 강제 GC, OS 메모리 반환 호출, 임의의 큰 요청으로 기준 RSS를 높이는 처리는 추가하지 않습니다.

검사 결과에는 초기화 시작/종료 시각, 5초 주기의 초기화 표본, heartbeat 4회, 16회 재연결의 수신 프레임 수를 별도로 기록합니다. 모든 연결이 30개 이상의 정상 이력 프레임을 받은 것을 확인해야 측정을 시작합니다. wrapper도 준비 완료와 측정 시작의 순서를 검사하므로 과거 도구가 만든 결과를 이번 완료로 처리할 수 없습니다.

이 방법도 실제 회복을 보장하지 않으며 실패하면 실패로 기록해야 합니다. 적용 전후 결과를 합산하지 않고, 기존 시작 직후 기준의 실패를 보존합니다. 60분 정규 관찰과 12회 정규 부하 비교의 완료를 대신하지 않습니다. 실제 결과는 [성능·자원 회귀 수정](performance-resolution.md)에 연결합니다.
